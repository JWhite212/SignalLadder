# Changelog

Notable changes to SignalLadder are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Latest Release on GitHub…**, beneath the version line in Settings, opens [the latest release](https://github.com/JWhite212/SignalLadder/releases/latest) in your browser, so you can compare its version with the copy you are running. SignalLadder checks nothing and makes no connection itself: your browser does, when you press the button. The address is fixed, so it carries nothing about your Mac or the build. The Settings window is taller to fit it. This is held by the tests, and was seen in the app on 2026-10-14, on macOS 27.2: pressed through the Accessibility API, the button opened the latest release in Chrome, and no connection by SignalLadder was seen. It has not been clicked with a mouse, or seen on macOS 14 or 15, in dark mode or with another browser.
- A test now holds the promise that SignalLadder's own code makes no network connection. It reads the search given under [What it never does](docs/privacy.md#what-it-never-does) from the privacy page and fails if any file under `Sources` matches it.

### Changed
- A rule with no escalation no longer cuts off a page. While the alert of a rule with an escalation is playing, its first alert, a repeat or its spoken line, a match on a rule without one plays nothing, and its Inspector row and the menu's last match read _Not played: a page was sounding_. It is not a failure and is not played later. A page still cuts off another page, and any alert still cuts off a plain one. This is held by the tests, and has not been seen in the app.
- Showing the Inspector, Settings or the On-Call Check now asks for the window to come back from the Dock if it was minimised, as the rule editor and the Setup Guide already did. On macOS 27.2 a minimised window came back without this, measured in a scratch program, so this makes the five windows alike and guards macOS 14 and 15, where it was not measured. This is held by the tests.
- ⌘W now closes the SignalLadder window in front: the rule editor, the Inspector, Settings, the On-Call Check or the Setup Guide. It does what the close box does, so the rule editor still asks about unsaved changes, and on the Setup Guide it counts as **Not now**. Before, no key closed any of them. There is still no Quit in the editor's menu. This is held by the tests, and has not been seen in the app.
- Opening SignalLadder again while it runs, from the Finder, Spotlight or Launchpad, now shows a window: the Setup Guide while setup is not finished, and Settings otherwise. Before, nothing happened, so with the menu bar icon hidden behind the notch or switched off there was no way in. If one of its windows is already open, that window comes forward instead. This is held by the tests, and has not been seen in the app.
- Granting Accessibility while SignalLadder runs now starts capture within a minute, without opening the menu. Before, capture started only when the menu opened, at launch or on the Setup Guide's **Check again**, so a grant made from the menu's own advice line, with the menu then closed, left every banner uncaptured until the menu was opened again. While Accessibility is not granted, SignalLadder now looks again every minute, and each look starts capture once it is granted. Opening the menu still starts it at once. This is held by the tests, and has not been seen in the app.
- When a save in the rule editor is refused because rules.json changed on disk, the sheet's default button is now **Cancel**, not **Reload from Disk**. Reload from Disk throws away your unsaved changes, so closing the editor, pressing Return on **Save** and Return again lost every edit without a word. It now comes last, is drawn as destructive, and the sheet says it discards your unsaved changes. This is held by the tests, and has not been seen in the app.
- An escalation the Mac slept through for more than 5 minutes still ends as _missed while asleep_, and plays nothing stale, but a Shortcut it had not yet run, such as the one that pages your phone, now runs once, at once, on waking, even if its delay had not run out. So does the page owed to a match that joined a burst. Before, the page was cancelled with the rest, so an alert the lid closed on never reached the phone. A Shortcut that had already run is not run again, and a page owed behind a run that was still out runs once that run has reported, unless you have acknowledged the miss. This is held by the tests, and has not been seen on a Mac that sleeps.
- **Reload Rules** no longer takes away the rules that were running when it cannot use the rules file: a hand edit that leaves it not valid JSON, a file that cannot be opened, or one written by a newer SignalLadder. Those rules keep running, and the menu says so, for example _⚠︎ Rules file could not be read — keeping the earlier rules: 3 active_, with the reason beneath. The icon still warns, and the on-call check says the file is not in effect. Before, one misplaced comma silenced every rule until the file was fixed. A file that loads still replaces the rules, even with fewer or every rule off, and so does removing the file, unless every rule in it that is on is refused (see below). The kept rules are in memory only, so SignalLadder starts with none if it quits before the file is fixed. This is held by the tests, and has not been seen in the app.
- A rule whose sound cannot be found or played, or whose voice is not installed, is no longer refused. It stays in effect, and the menu lists it under _⚠︎ 1 rule has a sound or voice that cannot be played — it is still in effect_, with the reason, as it lists a Shortcut that was not found. The icon turns to the slashed bell, the rule editor shows the reason beneath the rule's name as advice, and while you are on call the check counts it as urgent. An alert of it that would make no sound at all plays Sosumi, one of the macOS sounds, in its place, at the alert's own gain, and its row says so: _Could not play: sound "Klaxon" was not found; played Sosumi in its place_. A spoken alert whose voice is gone plays Sosumi and is never said in another voice. Refused, such a rule let the rules below it take its matches, so a `"silent"` rule beneath it, as in the README's own example, kept the page quiet. A sound file moved, or a voice an update removed, was enough. This is held by the tests, and has not been seen in the app.
- The line at the foot of Settings names the build number only when it differs from the version, so it no longer repeats the number. A build of 1.0.0 made from the source now reads _Version 1.0.0, built from_ the commit _on_ the date, where the 1.0.0 download reads _Version 1.0.0 (1.0.0)_. A build number that differs follows the version as _(build 7)_. This is held by the tests, and was first seen in the app on 2026-10-14, on macOS 27.2, as _Version 1.0.0, built from 0b378c0 on 14 Oct 2026_.
- A banner that SignalLadder reads a second time with more of its text now reaches your rules. It reads a banner again when a later read finds text the first did not, because a read can lose a line to a timeout, and the fuller text may match a rule the first read could not. When the later read kept the banner's description and gained only a line, such as the body, it was taken for a repeat of the first and dropped, so a rule that only the full text matched never sounded. Two banners whose descriptions were both lost were taken for each other in the same way. Now only a read with the same text, every line of it, within 1.5 seconds is a repeat. One banner still never sounds one rule twice: a second read within 1.5 seconds, with more of the same text or less, that matches the rule the first read set off plays nothing, asks no snooze and joins no escalation, and its Inspector row says _Already set off by an earlier read of this banner, no alert of its own_. That also stops the second sound a later read with less text, such as one that lost the description, used to set off. If the fuller text matches a different rule, that rule sounds as well, since it may be the one that pages. A follow-up from the same sender, which keeps the title and replaces the body, still sounds. This is held by the tests, and has not been seen in the app.
- A spoken alert starts about 45 milliseconds sooner, and a repeat that speaks no longer holds the app for that long first. SignalLadder listed every installed voice before each one; it now keeps the list, and lists again when the voices change, when the rules are reloaded, or when a voice is not in it. This is held by the tests, and has not been timed in the app.

### Fixed
- Expanding a stack of persistent alerts no longer makes SignalLadder capture the alerts in it again. On macOS 27.2 an expanded stack lays its older rows out as new elements, so every click on a stack, in Notification Centre's list or on the screen, read each of them as a notification that had just arrived, and a rule that matched an old alert sounded again. A notification keeps an identifier of its own through that, and SignalLadder now remembers the notifications it has captured by it: a row for one it has captured is passed over, and one whose text has changed, or that it never captured, is still captured. Measured on macOS 27.2 with SignalLadder's capture code run on its own beside the app, three expansions of a stack on screen captured 29, 32 and 29 alerts, of which 5, 7 and 5 were ones it had captured as they arrived; after the change they captured 28, 0 and 0, none of them one of those, and the 28 were older alerts it had never captured. In the open list, two expansions captured 34 and 33 before and 29 and 0 after. This is held by the tests ([#160](https://github.com/JWhite212/SignalLadder/issues/160)).
- Notifications that arrive close together are no longer half lost. One that arrives while another is on screen takes its place, and SignalLadder read 50 milliseconds after the first sign of it, by which time the next could already have taken its place in turn. Measured on macOS 27.2 with alerts from one app 0.05 seconds apart, it captured 7 or 8 of 12, and 4 of 12 at 0.02 seconds apart, and nothing said that any were missed. Now a notification that Notification Centre lays out and SignalLadder has not yet read is read at once. With SignalLadder's capture code run on its own beside the app, 12 of 12 were captured at 0.05 seconds apart and 11 of 12 at 0.02, three times each. Closer together than about 0.01 seconds, Notification Centre shows only the last of them, and the others still cannot be captured. This is held by the tests, and has not been seen in the app itself ([#154](https://github.com/JWhite212/SignalLadder/issues/154)).
- A rule's warnings are worked out again while SignalLadder runs, not only when the rules load: at each self-test, every 5 minutes on call and every 30 off, on waking, and when on-call mode is switched on. A Shortcut renamed or deleted, a sound file moved or a voice removed after the rules loaded is now warned about before tier 4 needs it, and on call the check window opens and the Mac beeps for a Shortcut that has gone. The rules file is not read for it. This is held by the tests, and has not been seen in the app.
- A tier 4 Shortcut that runs for more than a second and then stops with an error is reported as failed: _the Shortcut "Page me" started, then stopped with exit code 1_. It is held in the menu and on the row until that Shortcut starts again, and a page a joined match was owed is sent at once. Before, it counted as delivered and nothing said the phone was never paged. **Test Shortcut** shows such a failure beside the button. This is held by the tests, and has not been seen in the app.
- The rule editor's delete confirmation no longer reads a rule's name, or its Shortcut's, that is only a line break as a name. It asks _Delete this rule?_, as for a rule with no name, and says nothing of a Shortcut, as the loader and the rule warnings already treated such a name.
- Two copies of SignalLadder running at the same time no longer delete each other's Shortcut input. Each removes what is left in the shared folder at launch and at quit, so the second copy could delete the input of a Shortcut the first was still running. Each run's folder is now named for the process that made it, and a copy leaves another running copy's alone. This is held by the tests, and has not been seen in the app ([#106](https://github.com/JWhite212/SignalLadder/issues/106)).
- **Reload Rules** no longer takes away the rules that were running when the file loads but every rule in it that is on is refused, such as a file whose only rule has a misspelt key. Those rules keep running, and the menu says so, for example _⚠︎ Rules: 1 could not be used — keeping the earlier rules: 3 active_, with each refused rule beneath. The on-call check says the file is not in effect. Before, a typo in the only rule silenced everything, while the same typo in a file with another rule on silenced only that rule. A file with one rule on still replaces the rules, with the refused ones listed beside it. This is held by the tests, and has not been seen in the app ([#102](https://github.com/JWhite212/SignalLadder/issues/102)).
- The Setup Guide's first-rule step no longer leaves you stuck after you save a rule made from a banner without switching it on. Such a rule starts switched off and silent, so the step stayed unfinished and offered only **Make a Rule from This…**, which put a second identical rule beside the first. Now the step says you have rules and none is switched on and makes a sound, and offers **Edit Rules…**. Making a rule again from the same app, in the guide or the Inspector, selects the one already made if you have not changed it. This is held by the tests, and has not been seen in the app.
- **Open Notification Settings…**, in the Setup Guide and on the menu's advice line, now opens SignalLadder's own page in System Settings › Notifications, as it says. Before, it opened the top of Notifications, and you had to find SignalLadder in the list. Seen on macOS 27.2: the link opens the page titled SignalLadder.
- A rule editor that opened read-only, on a file it could not read or fully understand, now says what to do and has a **Reload Rules** button beside **Open Rules File in Text Editor**. Before, once you had fixed the file the window stayed read-only, and the way on was the menu's Reload Rules, which the window did not mention. This is held by the tests, and has not been seen in the app.
- If the acknowledge hotkey ⌃⌥⌘A could not be set up when SignalLadder started, most often because another app holds the same keys, the On-Call Check now says so, with a short line in the menu while you are on call. Before, only the log said so, and you found out by pressing it during an incident. It is not urgent: the panel and the menu still acknowledge. This is held by the tests, and has not been seen in the app.
- The On-Call Check window, which opens by itself with a beep when something new needs you, now gives most findings a button to where they are fixed. The health line opens the pane its cause names. A muted output or a zero Alert volume opens Sound. Rules findings open the rule editor. Apps not confirmed muted open the Setup Guide, and the Focus note opens Focus. Before, only the login finding had a button, so the rest named a problem and left you to find where to fix it. Each button only opens something. The Sound link was seen to open the Sound pane on macOS 27.2. The rest is held by the tests, and has not been seen in the app.
- An empty Inspector whose health is a problem now has a button for the System Settings pane its advice names, such as **Open Accessibility Settings…**, beneath the advice. Before, it gave the advice with no button, and the way on was the menu. This is held by the tests, and has not been seen in the app.
- The menu's advice line and the Setup Guide's **Prove it can read** step now open the System Settings pane that fixes the cause shown. _macOS is not exposing notifications…_ opens **Keyboard**, where its advice points, and _Not attached to Notification Centre_, which recovers by itself, opens nothing. Before, both opened Accessibility, which fixes neither. A missing grant still opens Accessibility, and the notification causes still open Notifications. The Keyboard link was seen to open the Keyboard pane on macOS 27.2. The rest is held by the tests, and has not been seen in the app.
- The rule editor now asks before it loses work you cannot get back. **Revert** asks, since it discards every change since you last saved. Deleting a rule asks when the rule has not been saved, has changed since you last saved, or ends in a Shortcut. In both questions **Cancel** is the default button. Before, both acted at once, and the editor has no undo. A saved rule you have not changed is still deleted at once. This is held by the tests, and has not been seen in the app.
- After the Mac's clock is set back, a notification with the same text as one just before the change is no longer taken for a repeat of it. SignalLadder drops a second read of the same text within 1.5 seconds, and a read dated before the clock moved counted as within them for as long as the clock had moved, so the notification reached no rule. This is held by the tests, and has not been seen in the app.
- A rule whose sound or voice name is only a line break is listed once, as a rule that cannot be used, and no longer also as one whose sound was not found. This is held by the tests.
- A self-test asked for while another was still being posted no longer starts beside it. When the first self-test's banner was captured before Notification Centre had finished taking the post, a second could start, and then the first never finished, or the second reported a failure for a capture that had worked, which counted against health and brought a retry. Now one runs at a time, as was intended. This is held by the tests, and has not been seen in the app.
- A notification that arrives while Notification Centre is open is captured even when the list was empty when it opened. SignalLadder takes the list for one closed and opened again when every row it opened with has gone, and one read that cannot find the list, which a read that times out also gives, was enough for that. An empty list has no rows to go, so it passed at once, and the next notification to arrive was taken for history and never reached your rules. This is held by the tests, and has not been seen in the app.
- The rule editor no longer quits when it shows a rule whose gain was edited by hand to a very large number, such as `"gainDB": 1e19`. The loader already refuses such a rule and lists why, but the editor still shows it, and writing the gain beside the slider crashed the app. The editor also writes a gain as it is, so a hand-edited 3.5 reads _+3.5 dB_, not _+3 dB_, as the Inspector already wrote it. This is held by the tests, and has not been seen in the app.
- When the rule editor cannot save, the alert now gives the reason in plain words, such as _You don't have permission to save the file “rules.json”…_, instead of a raw error dump beginning _Error Domain=NSCocoaErrorDomain_. A rules file that cannot be opened is described as it is in the menu. This is held by the tests, and has not been seen in the app.
- The rule editor now names its controls to VoiceOver, and a rule's priority can be set without a mouse. Each rule's tick box is read as the rule's name, not just "checkbox". Each row has **Move Up** and **Move Down**, both as VoiceOver actions and in its right-click menu, and these move the rule one place in the draft, just as a drag does. The ≡ handle is hidden from VoiceOver. The condition builder's three pickers and two **…** menus each say which one they are, such as _Condition field_ or _Group options_. The gain, rate and pitch sliders say their names, and the gain is read as _+12 dB_, not as a bare number. Each row of **Tried on recent notifications** is read as one line that begins with its verdict, _Matches_ or _Taken by a rule above_. Before, these marks were only icons. This is held by the tests, and has not been tried with VoiceOver.
- Dragging a rule in the rule editor's list moves it again. Each row allowed a move only while the pointer was over its handle (≡), and on macOS 27.2 that came to no move at all, so the order, which is the rules' priority, could only be changed with **Move Above**. Now the whole row can be dragged, the handle stays to show it, and a click on a rule's tick box still lands at once. A move changes the draft, marks it unsaved and is kept by **Save**. This is held by the tests. A list built the same way was dragged on macOS 27.2 with events posted to it, before and after the change, but the rule editor itself has not been dragged since, or on macOS 14 or 15.

## [1.0.0] - 2026-10-14

The first release with a signed and notarised download, as well as the source.

### Added
- Escalation runs. A rule can carry an escalation ladder beside its alert, written as `"version": 4`: a panel, a capped repeat, and a final alert or a Shortcut, each on its own timer from the match, until someone acknowledges it. See [Escalation](docs/rules-format.md#escalation).
- The rule editor sets up a ladder. Under a rule's first alert, **If I don't acknowledge** is a choice of Off, Gentle, On call or Wake me, with a sentence beneath it that says in words what the ladder does, and **Customise…** holds every control of tiers 2 to 4: each tier's switch and delay, the repeat's alert (with **Test Sound** or **Test Speech**), its interval and its two limits, each with **No limit**, and the last step as an alert or a Shortcut. Wake me repeats every 15 seconds with no limit on repeats or time until you acknowledge it, and the editor says beneath it that this keeps the Mac awake and sounding. The part about the Mac is a request to macOS that has not yet been tested on a Mac that can sleep. Choosing a preset leaves a Shortcut you added alone, and **Off** over a ladder that holds a Shortcut asks before it removes it. The file holds the explicit ladder, as before, and never the name of a preset. Beneath the ladder is one more switch, **Stay quiet while I have snoozed**, which is not a tier and which no preset touches: see Snooze for a meeting below. See [In the rule editor](docs/rules-format.md#in-the-rule-editor). The controls were drawn and driven in a test program outside the app, and have since been opened in the app itself. Their live checks are still to do. The switch was seen in the app on 2026-10-05, on macOS 26.7.1, unticked, with its caption for an unticked rule a snooze may hold. Ticking it has not been seen.
- **Test Shortcut**, beside a Shortcut's name in the rule editor, runs it for real with a made-up test notification whose four fields say it is a test, and shows _Started “Page me”_ or why it did not start. A failed test is shown beside the button and is never held in the menu.
- The escalation panel: a window over every app and every Space, full-screen apps included, that does not take focus. Over full-screen apps and other Spaces, that was seen in a test program on macOS 26.7, not yet in the app itself. It has one row per escalation, newest first, up to six with a count of the rest, naming the rule, when it started, how many matches it stands for once a burst has joined it and how far it has climbed, never what the notification said.
- You can acknowledge an escalation from its panel row, from **Acknowledge** or **Acknowledge All (N)** at the top of the menu, or with the hotkey ⌃⌥⌘A, which acknowledges all of them and does nothing when nothing is listed. It stops every tier still to come. The menu's item acts on the escalations it listed when the menu was opened, and leaves alone one that began while the menu was open and one that a match joined in that time. The hotkey acts on everything listed, including both, and a panel row's button acts on its own escalation. Acknowledging the last escalation stops the sound playing only if the latest alert to play was an escalation's, so it never cuts off an ordinary rule's alert. If the hotkey cannot be registered, its status code is logged and the menu and panel still work. On macOS 26.7 it needed no permission prompt.
- The menu says how many alerts are escalating, and how many matches they stand for once matches have joined them, so that they outnumber the alerts (_3 alerts escalating (14 matches)_), and how many were missed while asleep, and reports a Shortcut that did not run, with the reason. While an alert is escalating, the menu-bar icon alternates between a bell with sound waves and a filled one, and a problem's slashed bell takes precedence. A repeat or final alert that could not sound is reported like a first alert that could not. The menu never shows what a notification said.
- An Inspector row whose rule escalated has a line saying how far the ladder got, whether it was acknowledged, how many matches it stands for once a burst has joined it, and what its final alert or Shortcut did. It never shows what was spoken.
- An escalation that the Mac slept through for more than 5 minutes ends as missed while asleep when it wakes, instead of resuming hours-stale alarms, and stays on the menu, and on the panel if its panel had appeared, until you acknowledge it. A shorter sleep resumes the ladder. Sleep is measured as the time on the clock less the time the Mac was awake. Apple documents that the awake time does not count sleep, but this has not yet been checked on a Mac that sleeps.
- While any tier is still to fire, or a page is owed to a match that joined a burst, SignalLadder asks macOS not to let the Mac sleep on its own, and lets go once none is. It does not keep the display awake. This has not yet been tested on a Mac that can sleep.
- Quitting while an alert is listed, or while you are on call, asks first, because quitting stops every alert still escalating and a Shortcut not yet run will not run, and ends on-call alerting and the faster self-test. The question is not asked at a log out, a restart or a shut down, and it is not asked for 2 minutes after the system says one was requested. A quit that cannot be classified is asked about. If another alert begins while the question is up, or the total number of matches has grown because one joined an alert it named, choosing **Quit** asks again and names the new count and, when matches have joined, how many matches the alerts stand for. The totals are compared, so acknowledging another alert while the question is up can offset a match that joined, and then **Quit** goes ahead without asking again. See [Quitting asks whether to quit anyway](docs/troubleshooting.md#quitting-asks-whether-to-quit-anyway). The question was tested and its pieces tried in test programs. In the app, on macOS 26.7.1, it was seen asked on a menu Quit on 2026-10-02. A real restart with no prompt showing quit without one on 2026-10-02, and at a real log out on 2026-10-05, with the prompt already showing, the system's power-off notice answered it and SignalLadder exited cleanly. A shut down, a restart with the prompt showing and a log out with no prompt showing have not been seen.
- A rule naming a Shortcut that is not in the Shortcuts app is reported when the rules load.
- **On-call mode.** The menu's **On Call** item switches it on, with a tick, and the menu says since when (_On call since Mon 09:00_), so a switch you forgot is there to be seen. The time is saved, so the mode is still on after a relaunch, and it never switches itself off. Switching on runs a self-test at once, with another about two minutes later if it passes, and each is a real banner on whatever your screen shows. Switching off leaves escalations already running alone. It changes nothing a rule can read, and it is not the rule editor's **On call** choice, which the editor now says beside it: _On call applies whenever this rule matches, whether or not On-call mode is on._ See [On-call mode](docs/getting-started.md#on-call-mode). It is built and its decisions are tested, and it has been seen in the app in part, on macOS 26.7.1. On 2026-10-02 capture kept running with the status menu held open and with the quit prompt up, and the hold against idle sleep was taken at switch-on and released at switch-off. SignalLadder came back on call after a real restart on 2026-10-02, and after a real log out and the login that followed on 2026-10-05. On 2026-10-13, on macOS 27.2, the live check's `--on-call` run switched it on and off in the app, the menu showing the since-line and the saved date written and then gone, and passed. Its live checks are still to do. They include the status menu held still, the Mac kept awake on a Mac that can idle-sleep, the hold surviving an escalation ending, the check window on a real screen, the beeps at the Alert volume, and the icon at menu-bar size.
- A faster self-test while you are on call: every 5 minutes in place of every 30, about 12 banners an hour. The health line reads _Unverified_ once the last success is more than 6 minutes old in place of 31, and a failed self-test is retried after 60, 120 and 240 seconds and then every 5 minutes, where off call the retries go on doubling up to 30 minutes. There is no setting for the interval. Switching on drops a pending retry, since the self-test it runs takes its place, and switching off keeps one.
- The health beep repeats while you are on call. A fault beeps at once, then six more times 5 minutes apart, so seven beeps in the first half hour, and then every 30 minutes for as long as the fault stands. The banner still comes once. Capture that stays unverified for 10 minutes now counts as a fault, and so does capture still unverified 2 minutes after the Mac wakes, and each beeps on the same schedule with no banner. Off call it never sounds, as before. A self-test also runs when the Mac wakes while you are on call, and a healthy app may give one _did not complete_ beep right after a sleep, which the retry a minute later clears. The beeps are the Mac's alert sound, which macOS is reported to play at the Alert volume in System Settings › Sound and not at the output volume. That has not yet been tested.
- **Show On-Call Check…** opens an ordinary window, titled SignalLadder On-Call Check, that lists what SignalLadder can and cannot see: capture not yet verified or the health line's cause, a muted output while a rule sounds, an Alert volume of zero, rules that are not in effect, no rule enabled, rules that only show a panel, Shortcut names that were not found, apps not confirmed muted, and two standing notes, that a Focus hides banners and cannot be read and that a Mac that sleeps captures nothing and cannot be woken. Urgent findings come first, in sentences and counts, never naming a rule, an app or a Shortcut. It opens by itself when switching on finds something urgent and afterwards when something new turns up that the health alarm cannot see, with one beep, and with no beep for a muted output or an Alert volume of zero. **Check Now** runs one self-test and checks everything again. It is never a dialog.
- The menu-bar icon has an on-call state, a bell with a filled badge, described as _SignalLadder — on call_, with _self-test every 5 minutes_ added while self-tests are running. A problem's slashed bell outranks an escalation, which outranks a snooze's moon and the tray for what a snooze held, and those outrank it. While you are on call, capture that has stayed unverified, a muted or zero-volume output while a rule sounds, and an Alert volume of zero also show the slashed bell.

The last match is the second line of defence: if a real page comes in during the run, or `rules.json` is edited so that a rule of yours now comes first and takes a banner, the run stops there, posts no more banners and acknowledges nothing, and that escalation goes on, to its panel and its Shortcut if it has them, until you acknowledge it by hand. A capped escalation stays listed. When the run cannot show that the only thing escalating is the marker's, or cannot assert the count, it acknowledges nothing and exits 1, and if the marker's own escalation is the one listed it stays on the menu, escalating, until you acknowledge it by hand. The marker's panel shows on screen until the run acknowledges it.
  - `--on-call` switches on-call mode on, checks that the menu shows the since-line, that `rules.json` is unchanged and that the saved key `onCallSince` is written, and switches it off. It is your real on-call state: while it is on the Mac is held awake, SignalLadder runs a self-test, which shows a banner, and its check window may open. It writes nothing to `rules.json`.
  - `--snooze` adds a rule like the marker's, first in the rules array too, with a sound, set so that a snooze may hold it (Glass at −40 dB, with `quietWhenSnoozed`), chooses a 15-minute snooze, posts one banner under the marker's title, checks that the menu shows the marker's one match held and that nothing escalates, ends the snooze at once and dismisses the held summary only when it is the marker's one match. For as long as it runs, a snooze quiets your own rules that are set to stay quiet during one, as any snooze does.
  - **Each refuses to run, with exit 2 and changing nothing, on a Mac that belongs to a real shift:** `--on-call` and `--snooze` when SignalLadder is on call or snoozed, `--escalation` when something is escalating, and `--snooze` also when the menu already shows a held summary. It reads the menu before its default checks post a banner or open a window, and again just before it acts.
  - **Each puts back what it changed,** on a normal exit and on INT, TERM and HUP: it ends a snooze it began, dismisses the marker's held summary, switches on-call mode off if it switched it on, closes the on-call check window if it opened it, puts `rules.json` back byte for byte, chooses **Reload Rules** and checks that the menu shows neither _Snoozed until_ nor _On call since_ (as it found them, for `--escalation` on a Mac that was already on call or snoozed). A trap cannot run after a kill, a power loss or a crashed terminal, so each flag begins with a backup guard. It puts a leftover backup of `rules.json` back byte for byte only over a file that is still the one the earlier run wrote. When `rules.json` is already byte for byte the backup, there is nothing to put back, and it removes the backup. When it is neither, it refuses and leaves the files where they are.
  - The guards are functions in `Scripts/harness-guards.sh`. `Scripts/harness-guards-test.sh` runs every guard and every refusal as a case, 489 of them, with the marker writer on the layouts a rules file may have, against fixtures in `Scripts/fixtures/` and a temporary folder. It starts no app and posts no notification, and CI runs it as a step of its own after the tests, in both jobs.
  - **Run:** the script test passes, 489 cases. On 2026-10-13, on macOS 27.2, with the owner's approval, the script was run against a Developer ID build of `main` at `d41dfbd` (1.0.0, built with Xcode 27.1) in `/Applications`. By default it passed 15 of 15, and with `--on-call` 25 of 25, with `--snooze` 29 of 29 and with `--escalation` 27 of 27, each with exit 0 and each leaving `rules.json` byte for byte as it began. `--escalation` counted 5 matches against the 5 banners the log said were presented, which is the first time one escalation for a burst was seen in the app, on the script's own marker rule and banners. A default run on the script at `877ebc3`, which has the three fixes to the live check listed under Fixed, passed 16 of 16, with the check that its test banner was drawn passing. **Not seen:** a run interrupted with ^C, the run after a killed one, a real burst on your rules, and any of it on macOS 14, 15 or 26. Earlier runs of the flags' control flow in a scratch shell, against a stand-in for the app, were made when the script appended the marker rule at the end of the rules array, and are not claimed for the script as it now is. No run of the script test on CI's runners is recorded here.

### Changed
- A rule whose last step names a Shortcut that the Shortcuts app does not list is not refused. It stays in effect, first alert and repeats included, and tier 4 tries the name when it fires. The menu shows a ⚠︎ line under the rules summary with a line for the rule, the icon turns to the slashed bell, and the editor says so beside the name. A name typed by hand can be wrong by a typo or a capital, or a Shortcut can be renamed weeks later, and none of those should switch off a rule that also sounds and repeats. A name is still compared exactly, and a blank name is still refused.
- A Shortcut that did not run is held until that same Shortcut starts again, from an escalation or from **Test Shortcut**. A start of another Shortcut no longer clears it. Reloading the rules clears nothing, so after a name is changed in a rule the ⚠︎ line and the slashed bell stay until the old name starts again or SignalLadder quits. Within a burst a failed Shortcut is no longer left to wait: the next match that joins the escalation runs it again, once no run is still going, and each failure is held in its turn.
- When the Setup Guide opens, SignalLadder no longer asks macOS for Accessibility and for notifications at launch. The guide asks when you press the button of that step. When the guide does not open, because the Mac already has Accessibility and has not begun the guide, or the guide was finished or closed, SignalLadder asks at launch as it always did.
- Coming back to SignalLadder, after granting Accessibility in System Settings for instance, evaluates health again from what can be read at once and redraws the menu, so that the icon and the Inspector's health line change with the Setup Guide and do not wait for the next rebuild. It runs no self-test and asks nothing of macOS. That the icon and the line change at once has not been seen.
- `Scripts/verify-live.sh` finds the health line by what it says, so it works while an alert is escalating and its lines head the menu, and it fails and says so when no line says what a health line says. It reads the Inspector's and the rule editor's window titles out of `NotificationCore`, and `HarnessConstantsTests` holds the script to them.
- SignalLadder supports Apple silicon Macs only. It is built for arm64 with no Intel or universal build, and the README, the getting-started guide and the contributing guide now say so.
- `Scripts/verify-live.sh` reads every word it looks for or chooses out of `NotificationCore`, through one helper that it gets by sourcing `Scripts/harness-guards.sh`, and types none of the app's words. The status menu's capture-count stem and its **Show Inspector…**, **Edit Rules…** and **Reload Rules** titles are now constants in `StatusMenuText`, which the app builds its items from, so no word the menu shows changed. The other stems and titles the script looked for are constants where the app builds them, and its five health wordings are read from `HealthTitle`. The default run gains two checks: that no line on the menu begins with the setup line's stem, which fails the run on a Mac whose menu carries the setup line, and that **Settings…** opens a window titled SignalLadder Settings, which it closes. The cause reading steps over the setup line as it steps over the **On Call** item, so a Mac that carries the setup line and no cause no longer reports the setup line as a cause. `HarnessConstantsTests` scans every `.sh` file under `Scripts/` for the helper and for a word typed in place of a constant. The default run passed against a signed build on 2026-10-13, as the entry on the flags says.

Now the editor shows the same problem, **Save** is available for it without any edit, and the bar says which version the file declares and which version Save writes. The dry-run used to read as if such a rule were running. For a rule that is switched on, and for a rule below it, it now says _Not in effect until you save_.
- Clicking a stack of persistent alerts to expand it, or collapsing it again, no longer reads the alerts in it a second time. Each click used to add them to the Inspector again, timed to the click, and set off their rules' alerts again, an escalation included. A stack's accessibility description ends with ", stacked", which comes and goes as it expands and collapses while its text stays the same, and that was taken for new text. This was seen on macOS 26.7 with a test app's persistent alerts, not yet with Teams' or Outlook's.
- `Scripts/verify-live.sh` closes the Inspector it opens, as it closes the rule editor and Settings, and leaves an Inspector that was open before the run as it was. Every run against a signed build left it open until 2026-10-13.

- A match of the live check's marker rule no longer puts its app on the mute walkthrough's list. ### Security
- A Shortcut run by an escalation is given four fields of the notification (app name, title, subtitle and body) in a temporary file, each time it runs, which in a long escalation that a burst has joined can be more than once. It is the one place SignalLadder itself writes notification text to disk. It is in a folder of its own that only you can open, is deleted the moment the Shortcut ends, and anything a crash or quit left behind is removed at launch and at quit. What the Shortcut does with the text is up to the Shortcut you wrote.
- A live escalation keeps a copy of its notification in memory until it is finished with, which can be longer than the Inspector's last 50 rows. One that matches have joined may also keep the newest match it owes a page, a second copy in memory, until the page is sent or the escalation is acknowledged, ended by a sleep or finished with.
- SignalLadder now runs one other program, `/usr/bin/shortcuts`, and only for a rule that names a Shortcut: to list them, to run one as a last step, and to run one when you press **Test Shortcut** in the rule editor. Its output is never logged.
- **Test Shortcut** writes the Shortcut's temporary file too, with a made-up test notification and no notification you received. It really runs the Shortcut, so a Shortcut that sends a message sends it.
- SignalLadder's preferences hold a second key, `onCallSince`: the time on-call mode was switched on, in seconds since 1970. Switching off removes it. It is a date and not notification text, and a value there that cannot be read as a time reads as on-call mode being on.
- SignalLadder's preferences hold a third key, `launchAtLoginWanted`: a Boolean, what you last asked of the Launch at login switch. It is written only when you press the switch or a button that registers, and switching off writes false and does not remove it. A value that is not a Boolean reads as not wanted. It is not notification text.
- SignalLadder's preferences hold a fourth key, `snoozeUntil`: the end of a snooze, in seconds since 1970, as a real number. Ending a snooze, or finding one over, removes it. A value that is in the past, is not finite or is not a number reads as no snooze and is removed, and one further off than 2 hours is cut back to 2 hours and saved as that. It is a date and not notification text.
- SignalLadder's preferences hold a fifth key, `snoozeHeld`: what snoozes held and you have not dismissed, as one dictionary of numbers. `counts` maps a rule's id, as text, to a whole number of matches, `since` is the time of the first hold in seconds since 1970, `unannounced` is a whole number of matches held and not yet announced, and `unreadable` is the whole number 1, written only when an earlier record could not be read. It holds no rule name, no app name and no notification text, because a rule's name is looked up from the current rules when a line is shown. It is written whenever it changes, when a match is held, when what was held is announced, when a snooze that held something is ended and when you dismiss a line, and an empty summary removes the key. A record that cannot be read is said to have existed and never dropped.
- A snooze keeps no notification text anywhere: not in the saved values above, not in the menu's lines or the icon's tooltip, which hold the name of a rule you wrote and counts, and not in the Inspector row it adds, which is the row the match already had.
- SignalLadder's preferences hold a sixth key, `setupProgress`: how far the Setup Guide got, as one list of short fixed words: `started`, `introductionSeen`, `focusAttested`, `dismissed`, `finished`, and `skipped:` with the name of one of its eight steps. It is written whenever the guide records something, as the whole list, and read once, when SignalLadder starts. A word this version does not know is kept when the list is written back, and a value that is not a list reads as nothing saved. It holds no rule name, no app name and no notification text, and nothing the guide read: whether Accessibility is granted, what health says and which rules you have are read again each time.
- The Setup Guide keeps no notification text anywhere. It lists app names, read from banners, in the first-rule step and the mute step, and shows no title, subtitle or body. Its practice command is text to select, which SignalLadder neither runs nor copies to the clipboard.
- SignalLadder imports Apple's ServiceManagement framework, in one file, to register and unregister its own login item. It does so only when you press the switch or a button, and the core stays free of it.
- SignalLadder also reads, with no permission, what macOS reports for its own login item and the folder it is running from, to say whether Launch at login is on and whether it can be offered. A read changes nothing, and only the latest is held, in memory. The status is read when SignalLadder starts, at each health check, when the menu opens, when Settings is shown and when you come back to SignalLadder, among other times.
- SignalLadder reads the Mac's Alert volume, the global preference `com.apple.sound.beep.volume`, as a number, and never writes it. It reads the reason a quit carries and the system's notice that a log out, a restart or a shut down was requested, and keeps only the awake time of the latest notice, in memory.
- The log has a fourth category, `quit`: one line for every quit SignalLadder is asked about, holding the four characters of the quit's reason code, or none, and the age of any power-off notice, or none, at the default level and marked public. It holds nothing a notification said.
- The log has a fifth category, `loginitem`: one line for each request to register or unregister that failed, holding the error's domain and its code, marked public, at the error level. Never the error's description, which can hold a name or a path.

## [0.1.0] - 2026-09-29

The first tagged release. It is source only: there is no signed download yet, so you build it yourself ([getting started](docs/getting-started.md)).

### Added

**Capture**
- Reads notification banners from Notification Centre through the Accessibility API, and splits each into app, title, subtitle and body. It only reads: it never clicks, dismisses or replies.
- A notification that arrives while another banner is still on screen is captured, and each banner is read only once, however many times macOS redraws it. A banner read back with less text than before, because a read timed out, is not mistaken for a new notification.
- A second persistent alert from the same app, which macOS stacks with the first, is captured, and so is every alert after it in the stack. Teams alerts are persistent when Teams is set to Alert in System Settings.
- Opening Notification Centre does not replay the notifications it lists, however recent. SignalLadder recognises the list by how its window is built, checked on macOS 26.7, and a notification that arrives while the list is open is still captured. One that arrives at the very moment the list opens is taken for history, and may be missed.
- Capture recovers when Notification Centre restarts, however often it does.

**Health**
- A self-test: SignalLadder sends itself a silent notification and checks that it can read it back, at launch, two minutes later and then every 30 minutes. The menu shows _Working — verified 3 min ago_, _Unverified — last verified …_ once a self-test is overdue, _Cannot verify itself_ or _NOT capturing notifications_.
- Problems are reported three ways that no single fault can silence together: the menu-bar icon, a beep, and a notification when banners are known to be shown.
- The health line re-checks as soon as whatever blocked a self-test clears, such as Accessibility granted again or SignalLadder's own banners switched back on.
- Do Not Disturb is told apart from a capture failure, so Accessibility is not blamed for a notification that was never drawn.
- The app asks for Accessibility, then for notifications, and picks up a permission granted while it is running without a relaunch.

**The Inspector**
- **Show Inspector…** (⌘I): the last 50 captured notifications, newest first, with each field, the raw text on request, the banner type, how many the same app sent in the last hour, which rule matched and what was done. Held in memory only, and gone when the app quits.
- An empty Inspector says whether nothing has arrived or capture cannot be confirmed, and why.

**Rules**
- Rules in `~/Library/Application Support/com.jamiewhite.signalladder/rules.json`. A rule matches on `app`, `title`, `subtitle`, `body`, `raw` or `subrole` with `equals`, `notEquals`, `contains` or `matches` (a pattern with `*` and `?`), combined with `and`, `or` and `not`. Matching ignores case and accents, and the first enabled rule wins.
- One bad rule never disables the others. Problems, including a sound or voice that is missing, are listed by rule when the rules load, and a damaged file is reported, never overwritten. Unknown keys are errors, so a typo cannot leave a rule quietly silent.
- A rules file is written at the oldest version that can hold it (`1`, `2` with an alert, `3` with speech), so an older build refuses a file it cannot fully read rather than dropping part of it.
- **Reload Rules** (⌘R) previews new rules against everything already captured. The menu shows the rules in effect, the last match, and how many recent notifications the current rules match.
- [`docs/rules-format.md`](docs/rules-format.md), a guide to writing rules by hand.

**The rule editor**
- **Edit Rules…** (⌘E). Rules can be added, duplicated, deleted, switched on and off, and dragged into priority order. A condition builder handles nested _all of_, _any of_ and _not_ groups.
- A live dry-run shows which notifications in memory a rule would match, which rule above it takes others first, and **Move Above** to fix that. It always says whether what you see is in effect yet.
- **Make a Rule from This…** on every Inspector row, and **Add Condition from This Notification**, so a rule starts from a real notification.
- Safe saving: the file is written in one step, the version it replaces is kept as `rules.previous.json`, and a save is refused if the file changed on disk since it was read, with **Reload from Disk**, **Save Anyway** and **Cancel** offered. Save Anyway keeps a dated copy of what it replaces.
- A rules file the editor cannot fully represent opens read-only, with the reason. Closing the editor or quitting with unsaved changes asks whether to save. **Open Rules File in Text Editor…** opens the file itself.

**Alerts**
- A rule's alert can be a sound, a spoken line, both, or `"silent"`, which claims a notification and keeps it quiet.
- Sounds are the macOS sounds or your own files in `~/Library/Application Support/com.jamiewhite.signalladder/Sounds/`, up to 30 seconds long, at a gain from −40 to +12 dB. Every sound is level-matched, so at 0 dB each one peaks at the same level, with a limiter as a safety net.
- A spoken line comes from a template using `{app}`, `{title}` and `{body}`; the default is `{app}: {title}`, and it stops at 240 characters. Each spoken alert has its own voice, rate, pitch and gain, and speech is level-matched per voice. A voice that is not installed is reported, never replaced by another.
- **Test Sound** and **Test Speech** play an alert as it will sound. Test Speech reads a made-up notification, and neither interrupts a real alert.
- A new alert cuts off one still playing, including its speech, so two alarms never sound together.
- The Inspector and menu say what was done without claiming it was heard, such as _Played Glass (+6 dB)_, and note when the Mac's output was muted or at zero volume. The Inspector shows exactly what was said; the menu never does.
- A mute walkthrough in the menu offers **Open Notification Settings for …** and **I've Turned Its Sound Off** for each app a sounding rule reaches, and points to Focus settings. SignalLadder cannot check that an app is muted, and says so.

**The project**
- Released under the GNU General Public License v3.0, with a [contributor licence agreement](CLA.md) for contributions.
- A user guide in [`docs/`](docs/README.md): getting started, privacy and permissions, troubleshooting, and how the app works. A README, contributing guide, security policy, code of conduct, issue forms and continuous integration on macOS 15 and 26.

### Security
- Notification text is held in memory only, and never written to disk or to the logs. The only text on disk is what you put in a rule yourself.
- The mute checklist stores a one-way hash of each app name, never the name, because a name can come from a notification.
- The `signalladder-probe` developer tool prints notification text only when run with `--show-content`.
