# M1 capture findings — macOS 26.7

**Date:** 2026-09-11
**Machine:** Mac mini, macOS 26.7 (build 25G229), Apple Silicon
**Probe:** `signalladder-probe` at commit f106873, Developer ID signed

---

## Verdict: capture is viable

Notification banners **are** reachable in the accessibility tree. The macOS 15.4-class blindness case did **not** occur, and no assistive-technology client (VoiceOver, Full Keyboard Access) was needed to make the tree materialise.

## FINDING 1 — the description format is not what the spec assumed

**This invalidates spec §5.4 and the Task 5 implementation as designed.**

|                   |                                                                     |
| ----------------- | ------------------------------------------------------------------- |
| Spec assumed      | `"AppName, Title\nBody"` — split on first comma, then first newline |
| Actually observed | `"Script Editor, Test Title, Test Sub, Placeholder body"`           |

There is **no newline at all**. The format is comma-joined across _four_ fields: app, title, subtitle, body. The "split on first newline" half of the extractor would never fire, putting the entire remainder into `title` and leaving `body` permanently empty.

The heuristic is also worse than the spec feared. With commas as the only separator, a sender name, title, or body containing a comma is indistinguishable from a field boundary — and unlike the newline case there is no second delimiter to fall back on.

## FINDING 2 — the children carry the fields cleanly

The banner's `AXStaticText` children expose title, subtitle and body as **discrete values**, with no parsing required:

```
AXStaticText value="Test Title"
AXStaticText value="Test Sub"
AXStaticText value="Placeholder body"
```

This is strictly better than parsing the concatenated description and should become the primary extraction path. The description is still needed for the **app name**, which appears only as its first comma-delimited segment and has no child element of its own.

**Revised extraction strategy:**

- `appNameGuess` — text before the first comma in `AXAttributedDescription`
- `title` / `subtitle` / `body` — from the ordered `AXStaticText` children, mapped by count:
  - 1 child → title
  - 2 children → title, body
  - 3 children → title, subtitle, body
- `rawText` — the full description, preserved as the escape hatch

Comma-parsing of the description is demoted to a fallback for when no text children are present.

## FINDING 3 — subtitle is a real field the spec omits

macOS notifications carry a subtitle, and it appears as its own child element. The spec's `Field` enum (§5.7) has `app`, `title`, `body`, `raw`, `subrole` — no `subtitle`. It must be added, or subtitle content becomes unmatchable.

## FINDING 4 — notificationcenterui hosts many non-notification windows

The process owns 12+ windows at all times: Weather, Clock, Calendar, Reminders, Screen Time and Outlook widgets. Only one is the banner container.

Implications:

- The 256-node visit budget could plausibly be consumed by widget windows before reaching a banner, if a search ever starts from the application element rather than from the callback's window. `AXBannerWatcher.handle(element:)` traverses only the element handed to the callback, so the production path is unaffected — but this is a real trap for any future code that walks from the app root.
- Widget content is **personal data** (calendar entries, locations, screen-time app usage) and must never be captured or logged. The subrole allowlist already excludes it; worth keeping that way deliberately, not incidentally.

## FINDING 5 — TCC trust attribution

The probe reports `Accessibility trusted: true` when run from a development harness _and_ from the user's own Terminal. Under the harness this is unreliable — macOS attributes TCC to the responsible parent process, so a child of an already-trusted app inherits trust. Only the reading taken from the user's own Terminal is evidence.

**Open:** it is not yet confirmed whether the signed bare binary holds its own grant or is inheriting the terminal's. This matters for M2's onboarding design — the shipping `.app` bundle will hold its own identity, but a CLI probe may not.

## Signing

Developer ID signing produces a stable Designated Requirement:

```
identifier "com.jamiewhite.signalladder.probe" and anchor apple generic
  and certificate leaf[subject.OU] = RVVRP4WY6B
```

Verified byte-identical after a rebuild and re-sign, confirming the TCC grant survives rebuilds. Ad-hoc signing does **not** work for this: the `--identifier` flag is silently dropped and the DR degrades to a bare cdhash that changes every build.

## FINDING 6 — Teams uses a different subrole, and the allowlist saves us

A Microsoft Teams notification captured at 09:58:26:

```
AXGroup subrole=AXNotificationCenterAlert
        desc="Microsoft Teams, This is a test notification, Message preview."
├── AXStaticText value="This is a test notification"
└── AXStaticText value="Message preview."
```

The subrole is **`AXNotificationCenterAlert`**, not `AXNotificationCenterBanner`. This is not an app difference — it reflects the per-app _notification style_ set in System Settings: Banner (transient) versus Alert (persistent). Teams is configured as Alert on this machine.

**Consequence:** allowlisting only `AXNotificationCenterBanner` would have silently missed every Teams notification — the exact app the product exists for. The four-subrole allowlist inherited from the spec is load-bearing, not defensive padding.

It also means the subrole is **user-configurable per app** and can change without warning. Rules should not depend on it, and the Inspector must surface it so a style change is visible rather than mysterious.

Structure is otherwise identical to the Script Editor sample: comma-joined description, fields as discrete `AXStaticText` children. This confirms the two-child mapping (title, body) with real data.

## FINDING 7 — content-keyed dedupe is not safe for production

Banner animation fires `kAXWindowMovedNotification` repeatedly for the same banner, so the probe must collapse repeats. The probe does this by keying on the description text within a short window.

That is adequate for a diagnostic but **wrong for the product**: text equality cannot distinguish one banner re-firing from two genuinely distinct notifications carrying identical text — two consecutive identical alerts from a noisy channel are exactly the shape of traffic this app exists to handle. Content-keyed dedupe would drop the second.

The probe now **reports every suppression to stderr** rather than dropping silently, so the evidence it produces stays trustworthy. The production pipeline must instead key on **element identity**, which requires exposing identity through `AccessibilityNode` — deferred to the milestone that builds the real pipeline.

## FINDING 8 — known limitation: dedupe collides on empty descriptions

A banner is emitted when _either_ its description or its text children carry content, so a banner with an empty description now reaches the dedupe stage carrying `rawText: ""`. Because dedupe keys on `rawText` alone, two genuinely distinct banners that both have empty descriptions collide on the key `""`, and the second is reported as a suppressed repeat rather than emitted.

This is **visible, not silent** — the stderr suppression line still fires — but it mischaracterises a distinct notification as a duplicate.

Deliberately not patched. It manifests only in the partial-blindness state, which already indicates something is wrong, and the correct fix is the element-identity dedupe recorded in Finding 7. Keying on children content instead would be a third approximation of a heuristic already scheduled to be replaced properly.

**Action for the milestone that builds the real pipeline:** implement element-identity dedupe, which closes Finding 7 and this together.

## Still unknown

- **Microsoft Teams notification format.** Only a `Script Editor` test notification was captured. Teams is the app the entire project exists to handle, and its field layout is unverified.
- **Whether an @-mention is distinguishable** from ordinary channel chat in the captured fields. If it is not, the user's core rule cannot be expressed as designed.
- **Stacked notifications.** No `AXNotificationCenterBannerStack` was observed, so the deepest-match-wins behaviour added to `BannerTreeLocator` in Task 4 remains untested against real macOS output.
- **Whether banners appear at all during a Focus mode**, which the spec flags as a likely gap.
