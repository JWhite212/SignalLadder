## FINDING 1 — the description format is not what the spec assumed

**This invalidates spec §5.4 and the Task 5 implementation as designed.**

|                   |                                                                     |
| ----------------- | ------------------------------------------------------------------- |
| Spec assumed      | `"AppName, Title\nBody"` — split on first comma, then first newline |
| Actually observed | `"Script Editor, Test Title, Test Sub, Placeholder body"`           |

There is **no newline at all**. The format is comma-joined across _four_ fields: app, title, subtitle, body. The "split on first newline" half of the extractor would never fire, putting the entire remainder into `title` and leaving `body` permanently empty.

The heuristic is also worse than the spec feared. With commas as the only separator, a sender name, title, or body containing a comma is indistinguishable from a field boundary — and unlike the newline case there is no second delimiter to fall back on.

## FINDING 2 — the children carry the fields cleanly

The banner's `AXStaticText` children expose title, subtitle and body as **discrete values**, with no parsing required:

```
AXStaticText value="Test Title"
AXStaticText value="Test Sub"
AXStaticText value="Placeholder body"
```

This is strictly better than parsing the concatenated description and should become the primary extraction path. The description is still needed for the **app name**, which appears only as its first comma-delimited segment and has no child element of its own.

**Revised extraction strategy:**

- `appNameGuess` — text before the first comma in `AXAttributedDescription`
- `title` / `subtitle` / `body` — from the ordered `AXStaticText` children, mapped by count:
  - 1 child → title
  - 2 children → title, body
  - 3 children → title, subtitle, body
- `rawText` — the full description, preserved as the escape hatch

Comma-parsing of the description is demoted to a fallback for when no text children are present.

## FINDING 3 — subtitle is a real field the spec omits

macOS notifications carry a subtitle, and it appears as its own child element. The spec's `Field` enum (§5.7) has `app`, `title`, `body`, `raw`, `subrole` — no `subtitle`. It must be added, or subtitle content becomes unmatchable.

## FINDING 4 — notificationcenterui hosts many non-notification windows

The process owns 12+ windows at all times: Weather, Clock, Calendar, Reminders, Screen Time and Outlook widgets. Only one is the banner container.

Implications:

- The 256-node visit budget could plausibly be consumed by widget windows before reaching a banner, if a search ever starts from the application element rather than from the callback's window. `AXBannerWatcher.handle(element:)` traverses only the element handed to the callback, so the production path is unaffected — but this is a real trap for any future code that walks from the app root.
- Widget content is **personal data** (calendar entries, locations, screen-time app usage) and must never be captured or logged. The subrole allowlist already excludes it; worth keeping that way deliberately, not incidentally.

## FINDING 5 — TCC trust attribution

The probe reports `Accessibility trusted: true` when run from a development harness _and_ from the user's own Terminal. Under the harness this is unreliable — macOS attributes TCC to the responsible parent process, so a child of an already-trusted app inherits trust. Only the reading taken from the user's own Terminal is evidence.

**Open:** it is not yet confirmed whether the signed bare binary holds its own grant or is inheriting the terminal's. This matters for M2's onboarding design — the shipping `.app` bundle will hold its own identity, but a CLI probe may not.

## Signing

Developer ID signing produces a stable Designated Requirement:

  and certificate leaf[subject.OU] = RVVRP4WY6B

## FINDING 6 — Teams uses a different subrole, and the allowlist saves us

A Microsoft Teams notification captured at 09:58:26:

```
AXGroup subrole=AXNotificationCenterAlert
        desc="Microsoft Teams, This is a test notification, Message preview."
├── AXStaticText value="This is a test notification"
└── AXStaticText value="Message preview."
```

The subrole is **`AXNotificationCenterAlert`**, not `AXNotificationCenterBanner`. This is not an app difference — it reflects the per-app _notification style_ set in System Settings: Banner (transient) versus Alert (persistent). Teams is configured as Alert on this machine.

**Consequence:** allowlisting only `AXNotificationCenterBanner` would have silently missed every Teams notification — the exact app the product exists for. The four-subrole allowlist inherited from the spec is load-bearing, not defensive padding.

It also means the subrole is **user-configurable per app** and can change without warning. Rules should not depend on it, and the Inspector must surface it so a style change is visible rather than mysterious.

Structure is otherwise identical to the Script Editor sample: comma-joined description, fields as discrete `AXStaticText` children. This confirms the two-child mapping (title, body) with real data.

## FINDING 7 — content-keyed dedupe is not safe for production

Banner animation fires `kAXWindowMovedNotification` repeatedly for the same banner, so the probe must collapse repeats. The probe does this by keying on the description text within a short window.

That is adequate for a diagnostic but **wrong for the product**: text equality cannot distinguish one banner re-firing from two genuinely distinct notifications carrying identical text — two consecutive identical alerts from a noisy channel are exactly the shape of traffic this app exists to handle. Content-keyed dedupe would drop the second.

The probe now **reports every suppression to stderr** rather than dropping silently, so the evidence it produces stays trustworthy. The production pipeline must instead key on **element identity**, which requires exposing identity through `AccessibilityNode` — deferred to the milestone that builds the real pipeline.

## FINDING 8 — known limitation: dedupe collides on empty descriptions

A banner is emitted when _either_ its description or its text children carry content, so a banner with an empty description now reaches the dedupe stage carrying `rawText: ""`. Because dedupe keys on `rawText` alone, two genuinely distinct banners that both have empty descriptions collide on the key `""`, and the second is reported as a suppressed repeat rather than emitted.

This is **visible, not silent** — the stderr suppression line still fires — but it mischaracterises a distinct notification as a duplicate.

Deliberately not patched. It manifests only in the partial-blindness state, which already indicates something is wrong, and the correct fix is the element-identity dedupe recorded in Finding 7. Keying on children content instead would be a third approximation of a heuristic already scheduled to be replaced properly.

**Action for the milestone that builds the real pipeline:** implement element-identity dedupe, which closes Finding 7 and this together.

## FINDING 9 — re-attach was structurally broken, and only live testing found it

The watcher's recovery path depended on `NSWorkspace.shared.notificationCenter` launch/terminate notifications. **Those are never delivered to a non-GUI CLI process.** The entire mechanism was built on an event that cannot fire in this process type.

Evidence, from an instrumented build:

```
DIAG heartbeat attachedPid=8781 livePid=8781 observer=set
DIAG heartbeat attachedPid=8781 livePid=9587 observer=set   <- restarted, unnoticed
```

Zero workspace events arrived for _any_ application during that window, despite `killall` having just terminated one.

This is the product's worst failure mode — permanent silent blindness — sitting inside the mechanism meant to prevent it. An `AXObserver` bound to a dead process reports no errors. It simply goes quiet.

**It would have passed any code review.** Three reviewers read that watcher closely; none could have caught it, because the defect exists only at runtime and only in this process type. Nothing short of running it and killing the target would have surfaced it.

**Fix:** a `DispatchSourceProcess` watching the attached PID for `.exit` — event-driven, and independent of process type. `NSWorkspace` observation is retained as a _secondary_ signal because it will fire once this runs inside a real `.app` bundle. Two independent detectors, neither trusted alone.

Verified live:

```
[watcher] notificationcenterui (pid 9587) exited; scheduling re-attach
[watcher] attached to notificationcenterui pid=10782
```

followed by normal captures. Recovery confirmed against a real process restart.

**Design lesson for the milestones that follow:** the spec's §9 health canary is not optional polish. This class of failure produces no error, no exception and no log — only silence. Only a check that actively proves the pipeline still works can detect it.

## M2b verification (2026-09-11) — and the bug it found

Task 6 was written as a human checklist. It did not need to be: the menu is
readable over the Accessibility API, notifications are postable with
`osascript`, and the unified log holds the delivery evidence. `Scripts/verify-live.sh`
now automates everything except the three steps that change a system security
setting. Run it instead of reading a menu by eye.

### Measured

|                  |                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Idle CPU         | **0.00%**, sampled over 10s with no interaction (`ps -o time=` delta — `%cpu` is a lifetime average and reports the observer's own effect) |
| Resident         | 60 MB                                                                                                                                      |
| Capture          | confirmed live, count increments exactly once per posted banner                                                                            |
| Canary exclusion | confirmed — a successful launch canary leaves the count at 0                                                                               |

### The failure, and what it exposed

The menu reported _"Cannot verify itself — a self-test did not complete"_ while
capture was demonstrably working. The unified log settled it:

```
mode: Do Not Disturb (com.apple.donotdisturb.mode.default), since 14:13:18 +0000
canary → outcome: suppressed; interruptionSuppression: delay delivery;
         intelligentBehavior: silence
         visibility: [history, alert, muted, ...]  canDisplayWhileCenterIsClosed: false
```

**Do Not Disturb was on.** The self-test was accepted and routed straight to
history with no banner drawn, so the Accessibility layer had nothing to see and
the round trip timed out — correctly. The health alarm five seconds later was
swallowed the same way, which is the three-channel design working: the glyph and
the beep do not depend on notifications.

Four defects behind it, all now fixed:

1. **The app sent the user to the wrong settings pane.** `selfTestInconclusive.isDeliveryFault`
   was `false`, so the advice line opened Accessibility — offering to re-grant
   Accessibility to cure a Do Not Disturb. `CaptureHealth`'s own doc comment warns
   against exactly this in exactly these words. Now `true`: when the fault cannot
   be attributed, stop accusing the half that is probably innocent.
2. **"Will re-check shortly" was false.** Menu opens run `refreshHealth(runCanary: false)`,
   so the next self-test was up to 30 minutes away. Observed live: the display was
   still wrong fourteen minutes after the DND causing it had been switched off, while
   capturing normally throughout. Now retries at 60s, backing off to the 30-minute cadence.
3. **Delivery faults were invisible.** `DeliveryStatusProbe` reads `alertStyle`, which
   is unchanged by DND, so `wouldDisplay` was `true` while the notification was being
   muted. Closed without any entitlement by counting accessibility events across the
   self-test: **a drawn banner creates a window and therefore an event even if reading
   it then fails; a suppressed one creates nothing.** Zero events across a failed
   self-test now reports `notificationsSuppressed`, and repeated suppression no longer
   escalates to `blind` — otherwise a quiet evening under DND would end with the app
   insisting Accessibility was broken.
4. **No diagnostic trail existed.** `AXBannerWatcher.log` wrote to stderr on the belief
   that a LaunchServices-started `.app` has stderr captured by the unified log. It does
   not — a live run produced notification-subsystem entries for this app and not one line
   from ours. Now `os_log` under subsystem `com.jamiewhite.signalladder`:

   ```
   /usr/bin/log show --last 30m --predicate 'subsystem == "com.jamiewhite.signalladder"'
   ```

   (`log` is a zsh builtin; the absolute path is required.)

Also fixed, found by review rather than by the failure: the canary's marker was
matched only against the banner's accessibility description, which the capture path
explicitly tolerates being empty. A self-test could therefore fail on a banner that was
captured perfectly. It now matches the text children too, and `SelfNotification` carries
the self-test title as a backstop so a marker miss cannot inflate the user's count.

### ANSWERED: are banners drawn during a Focus or DND?

**No.** Logged as an open unknown since M1 and flagged in the spec as a likely capture
gap. It is confirmed: under Do Not Disturb, macOS draws no banner and the notification
goes straight to history, `muted`. **SignalLadder captures nothing while DND is on.**

This is a product constraint, not a bug, and it lands badly for an on-call tool — the
hours you most want escalation are the hours DND is most likely on. Apps allowed to
break through DND still draw banners, so the workaround is to grant break-through to
the source app (Teams) and let SignalLadder route beneath it. **M3's on-call mode has to
account for this**, and onboarding has to say it out loud.

### A script bug found while wiring this up

The brief's literal AppleScript block for opening the Inspector —
`INSPECTOR=$(osascript <<'APPLESCRIPT' ... APPLESCRIPT)`, with `set AppleScript's text
item delimiters to linefeed` inside the heredoc — does not parse under `/bin/bash` as
shipped on macOS (GNU bash 3.2.57). That bash has a known defect: a heredoc containing
an apostrophe, when the heredoc sits directly inside a `$(...)` command substitution,
makes the parser lose track of the closing paren and fail with `unexpected EOF while
looking for matching` `''`. `bash -n Scripts/verify-live.sh` reproduces it directly.

The existing `read_menu` helper never hit this because its heredoc (which contains the
same apostrophe) is a bare statement inside a function body — the function is called as
`$(read_menu)`, so the heredoc itself is never nested inside the substitution. The fix
applied here follows that same shape: the new AppleScript was moved into a
`read_inspector_windows()` function, called as `INSPECTOR=$(read_inspector_windows)`.
The AppleScript text itself is unchanged, byte-for-byte, from the brief.

## OPEN: capture stopped working on this machine (2026-09-11, during M2c verification)

**Status: live, unresolved, NOT caused by M2c.** Recorded here because the next
person to see an empty Inspector needs to know this happened.

Recurred on 2026-09-25 and cleared on a plain relaunch. See
"M3b live verification (2026-09-25)" at the end of this file.

### Symptom

Banners are drawn — confirmed in Apple's own log, `canDisplayWhileCenterIsClosed: true`,
no `muted` in the visibility list — and the capture count stays at zero. The app
is attached to the live Notification Centre process and receives no accessibility
events at all.

### What was ruled out

| Check | Result |
|---|---|
| Is it an M2c regression? | **No.** Rebuilt `master` at 54b4cc0, relaunched, posted a notification: identical failure, count 0. The control is the decisive fact. |
| Is Accessibility revoked? | No — health would report `accessibilityNotTrusted` first, and does not |
| Is the observer attached? | Yes — `attached to notificationcenterui pid=21246`, and that pid is the live `NotificationCenter.app` |
| Did Notification Centre restart? | No — running since 13:44, no re-attach logged |
| Is Do Not Disturb on? | No — inactive, confirmed from `donotdisturbd` state |
| Is the AX tree exposed at all? | **Yes** — System Events reads `count of windows` from the NotificationCenter process successfully |

So: the tree is readable, the observer is registered against the right live
process, and `kAXWindowCreatedNotification` simply never fires for us.

### Most likely cause and the thing to try

This matches `HealthCause.lazyAccessibilityTree` — macOS not delivering
notification accessibility events to an assistive client. **Full Keyboard Access
is OFF on this machine** (`com.apple.Accessibility KeyboardAccessEnabled` absent),
and turning it on is the documented workaround. That is a system setting, so it
needs a person.

Worth noting the app had been rebuilt and relaunched roughly six times in the
fifteen minutes before this started, each with a fresh code signature. Whether
rapid re-signing contributes is unknown and worth watching.

### What this exposed, and it is the important part

While blind, the app reported: *"Do Not Disturb, a Focus, or an alert style of
None is suppressing SignalLadder's own alerts."* Do Not Disturb was off. It was
not suppressed. It was blind, and it blamed Notification Centre.

That inference came from the M2b fix for the opposite error — where a DND-suppressed
self-test was blamed on capture. "No accessibility event during the self-test"
was read as "the banner was never drawn", which only holds if the accessibility
path is healthy, and that is precisely the path in question. Fixing the first
error introduced its mirror image.

Both causes produce identical evidence: nothing happened. `selfTestAlertNeverSeen`
now says so, names both, and tells the user which to rule out first. Commit a28f23f.

**The general lesson, which has now cost five separate bugs in this project:**
absence of a signal is never evidence for one specific cause when the detector
itself is one of the suspects.

## M3b groundwork (2026-09-24): muting cannot be verified — and one file would lie about it

Checked before designing M3b's mute walkthrough, which the spec calls "trust-based;
unverifiable" (§3, §8.2). The question was whether that is still true.

| Store | Last modified | Readable without extra permission |
|---|---|---|
| `~/Library/Preferences/com.apple.ncprefs.plist` | **2025-09-19** | yes |
| `~/Library/Group Containers/group.com.apple.usernoted/` | today | **no** — TCC-protected |
| `~/Library/DoNotDisturb/DB` | today | **no** — Full Disk Access (as the M2 Focus spike found) |

**`ncprefs.plist` is stale on macOS 26 and must never be used.** It still parses, holds 83
per-app entries with plausible `flags` bitmasks, and even a `dnd_prefs` block — but it was last
written a year ago, and SignalLadder, granted notification permission on 2026-09-11, is absent
from it. A "verified muted" feature built on it would report year-old settings as current: this
project's signature defect, designed in rather than slipped in. The live per-app settings are in
the usernoted group container, which is TCC-protected — and which also holds notification
*history*, i.e. content, which §13 excludes on its own terms.

Conclusion: the spec stands. Mute confirmation stays a manual, persistent, visible checklist, and
the Inspector's "Matched" column remains the empirical check (two sounds heard, row shows ours
fired ⇒ the other is the source app's).

Facts gathered for M3b, all read-only:

- **Teams resolves cleanly for the §8.2 lookup.** `/Applications/Microsoft Teams.app` is
  `com.microsoft.teams2` with display name `Microsoft Teams` — exactly the banner's `appNameGuess`.
  One running-app match, so the notification-settings deep link can target it directly.
- Weather is `com.apple.weather`.
- System sounds available to reference by name until a sound set is chosen (§15): Basso, Blow,
  Bottle, Frog, Funk, Glass, Hero, Morse, Ping, Pop, Purr, Sosumi, Submarine, Tink.
- The stale `dnd_prefs` block records a *setting* ("turn on Do Not Disturb when the display
  sleeps"), not live state — so it cannot detect DND either. But M2b's live log already showed DND
  engaged with `suppressionState: while UI locked`. **If this Mac enables DND whenever it locks or
  sleeps, SignalLadder is blind every time the user steps away — precisely when an on-call alert
  most needs to escalate.** The mute walkthrough must address this (break-through for the source
  app, or changing that Focus option), and it cannot be verified either.

### Audio (§5.16), measured offline and silently

`docs/dev/spikes/audio-headroom.swift` renders every system sound through the spec's graph
(player → `AVAudioUnitEQ.globalGain` → Apple PeakLimiter → mixer) using `AVAudioEngine` offline
manual rendering — nothing reaches a speaker — and measures peak level and samples over full scale.

| | Result |
|---|---|
| Source headroom | 5.4 dB (Hero) to 15.3 dB (Frog); most around 10 dB |
| +6 dB ("200%") with **no** limiter | 13 of 14 fine. **Hero clips**: 55 samples over, peak +0.59 dBFS |
| +6 dB with the limiter | All 14 at or below −0.05 dBFS, **zero** samples over |
| +12 dB with the limiter | All 14 at or below −0.01 dBFS, zero samples over |

The spec's caution that the limiter's attack "can momentarily exceed 0 dBFS" did not
materialise for these sounds. Two findings that change M3b's design instead:

1. **The EQ does not enforce its documented range.** §5.16 records `globalGain` as spanning
   −96 to +24 dB "(verified)". Setting +30 and +40 applied exactly +30 and +40 — Frog came out
   24.7 dB over full scale. With rules hand-written as JSON, a typo in a gain value would produce
   an ear-splitting alert. **The rule validator must clamp or reject gain itself**, and the limiter
   is load-bearing, not a nicety.
2. **The real problem is loudness, not clipping.** Frog peaks at −15 dBFS and Hero at −5 — a
   10 dB spread, which by §5.16's own note is roughly a perceived doubling. "200%" on Frog is still
   quieter than Hero at 100%. For an alert whose one job is to be heard, M3b should normalise each
   sound's peak at import (the measurement §5.16 already calls for, used for consistency rather
   than only clipping), so the gain control means the same thing for every sound.

### Speech (§5.9), rendered without being spoken

`docs/dev/spikes/speech-render.swift`. "Microsoft Teams: you were mentioned in All Hands"
in an en-GB voice:

- `AVSpeechSynthesizer.write(_:toBufferCallback:)` works as §5.9 intends: 278 buffers, ~3.2 s,
  nothing audible.
- **Buffers are float32, 22,050 Hz, mono** — not the sound files' format. Speech needs its own
  `AVAudioPlayerNode` connected at that format (the mixer converts); scheduling speech buffers on
  the sounds' player would fail.
- **Peak −1.32 dBFS: 1.3 dB of headroom.** Speech is ~10 dB hotter than most system sounds at the
  same setting, so any positive speech gain is pure limiter work, and a sound and a spoken alert
  at "100%" differ by roughly a perceived doubling. Normalise levels at the source.
- **The callback is delivered on the main thread.** The first run of the spike deadlocked by
  blocking main while waiting for it — the mistake M3b's implementation must not make.
- 184 voices installed, 45 English: 42 default quality, 3 enhanced, no premium, no Siri — as §5.9
  predicted, the picker can only offer what `speechVoices()` returns.
- Time from `write` to the first buffer: measured 2026-09-25. See "Speech latency" at the end of
  this file.

## M3b live verification (2026-09-25): capture went blind again, behind a "verified" health line

First run of `Scripts/verify-live.sh` against a freshly built `build/SignalLadder.app`: 9 passed,
1 failed. The test banner was drawn (not muted) and the capture count stayed at 0. The same
symptom as the open outage above, and it cleared the same undiagnosed way.

### Sequence

1. `Scripts/make-app.sh` rebuilt and re-signed the bundle in this worktree, and it was launched.
   **An older copy from the main checkout was still running.** For a short time two instances
   were attached to the same Notification Centre process. The old one was then killed.
2. `verify-live.sh` ran with the new instance **1 min 22 s** old. Health read
   **"Working — verified"**, and the test banner was not captured (count 0 → 0).
3. Killed and relaunched the same bundle, with no rebuild and no re-sign. Every run after that
   captured its test banner (0 → 1, 1 → 2, 2 → 3). Final run: 10 passed, 0 failed.

Full Keyboard Access was still off throughout (`KeyboardAccessEnabled` absent), so the
workaround suggested above was never applied and did not cause the recovery. Notification
Centre was not restarted either: one pid (819) throughout.

### What "verified" meant here, and why it was wrong

"Verified" only means that the last self-test banner was captured
(`consecutiveCanaryFailures == 0`). The self-test runs at launch and then every 30 minutes. So
capture really was working at launch, and stopped within about 80 seconds. After that,
health went on claiming "verified" from a result that no longer held, and it would have kept
doing so for up to half an hour.

This is the lesson recorded above, turned round: **an old success is not evidence of a current
one either.** "Verified" is a claim about one moment, and nothing about it ages. For an on-call
tool, half an hour of false reassurance is the failure that matters most. Options, none chosen:

- say how old the evidence is ("verified 12 min ago")
- re-run the self-test when real traffic stops reaching the capture path
- use a shorter interval after launch, when this has now happened twice

**Settled the same day: the first and third.**

- The health line says how old its evidence is: _Working — verified 3 min ago_. Once the
  evidence is older than the self-test interval plus a minute, a self-test that should have
  run has not. Health then becomes unknown, not verified, and reads _Unverified — last
  verified 34 min ago_. Staleness is missing evidence, not evidence of a fault, so it never
  sounds the alarm. (`HealthEvaluator`, `HealthTitle`.)
- A second self-test runs two minutes after one passes at launch, after a re-attach, or when
  capture starts. Both outages began within minutes of a relaunch. This would have caught
  today's within two minutes rather than thirty. It costs one banner, on an event that is
  rare.
- Not done: using real traffic, or its absence, as a trigger. Silence proves nothing, and
  traffic that arrived before capture died says nothing about after. A wake from sleep is not
  a trigger either. No outage has followed one, and a self-test that came due during sleep
  runs as soon as the Mac wakes anyway.

What remains: an outage that begins at any other time still reads _Working — verified N min
ago_ for up to 30 minutes. It no longer reads as a claim about the present, but it is still
up to half an hour of blindness. The on-call cadence (§14: 5 minutes) is the next lever. It
arrives with the on-call toggle (M5), and the evidence ages at whatever interval is passed in.

### What this adds to the open outage

| Observation | Bearing |
|---|---|
| Both occurrences came directly after a rebuild and relaunch with a fresh signature | Strengthens the "rapid re-signing" suspicion. Still unproven |
| This time the outage began *after* a successful capture, not from launch | The observer attached and worked, then stopped delivering. Not a failed attach |
| A plain relaunch cleared it, with no system setting changed | The Full Keyboard Access workaround is not the only way out. Relaunching is a cheaper first step |
| A second instance was attached at the same time | New variable, untested. Two assistive clients observing one process may matter |
| The test banner comes from `osascript`, the self-test from SignalLadder | Not ruled out: a banner that replaces one already on screen may not create a new window, so `kAXWindowCreatedNotification` would not fire |

**Next time it happens,** before relaunching: note whether another instance is running, whether
a banner with the same title was already visible, and how long the app had been up. Those
three facts separate the hypotheses above. A relaunch destroys the evidence.

## M3 live checks (2026-09-25): the rule editor, driven through Accessibility

The M3b and M3c plans left their live checks to a person, on the grounds that SwiftUI cannot
be read by the harness. It can. Through System Events, the editor's switches, radio buttons,
pop-ups, text fields, Save and Revert, the conflict sheet and the close prompt could all be
read and pressed. Every check that did not need a drag or a listener was run that way against a
build of `main` at 2e1e77e. Results are recorded against each checkbox in the two plans. What
the run found:

### ⌘X, ⌘C, ⌘V, ⌘A and ⌘Z did nothing in the editor's text fields — fixed

A text field does not handle those keys itself. AppKit delivers them through the main menu's
key equivalents, and an accessory app has no main menu unless it builds one. SignalLadder
did not. ⌘A in a condition's value field appended the typed text instead of replacing it, and
a channel name could not be pasted into a condition.

Fixed by giving the app a main menu that macOS never draws: an empty application menu and a
standard Edit menu (`MainMenu.swift`). There is deliberately no Quit item, so ⌘Q in the editor
cannot end alerting by accident. Checked on the rebuilt app: select all, undo, copy, paste and
cut each worked in a condition field. The clipboard was saved before the test and restored
after it.

**The fix changed what the harness sees.** With a main menu, the app has two menu bars, and
`menu bar 1` is the new one: `verify-live.sh` pressed its first item and opened the Apple menu.
The harness now finds the status item by its subrole, `AXMenuExtra`, which is right whether or
not a main menu exists. Against the fixed build: 12 passed, 0 failed.

### Nested ⋯ menus through Accessibility — retracted, a fault in the test

Reported first as: pressing any ⋯ menu through the Accessibility API opens the top-level
group's menu. The fault was in the test. System Events rewrote each reference to a ⋯ button as
`menu button "More"`, a lookup by name. All of them are named "More", so every press reached
the first one. Pressed with the raw Accessibility API (`AXUIElementPerformAction`), as
VoiceOver does, each ⋯ opens its own menu: the group's offers Add, Negate Group and so on, and
each condition's offers Negate, Group and Remove. Checked on the unchanged code the same day.
Four structural edits caused no crash.

### Smaller findings

- **Unnamed controls — retracted, also a fault in the test.** System Events showed no name
  for Save, Revert, Test Sound, Add Condition or the Inspector's "Make a Rule from This…" link.
  Read directly, each carries its label as `AXDescription`, which is what VoiceOver reads.
- **A rename reads as two changes — fixed.** The save-conflict sheet described a hand-renamed
  rule as `Added: "… (edited by hand)". Removed: "…"`, although the rule kept its `"id"`. Rules
  are now paired by id first, and the sheet says `Renamed: "…" to "… (edited by hand)".`
  Checked live. Files written by hand, with no ids, still compare by name.
- **Signing flakes — fixed.** `make-app.sh` failed with "A timestamp was expected but was not
  found" on about half of its runs, sandboxed or not. It is Apple's timestamp service, not the
  sandbox, as was first assumed. Debug builds now sign with `--timestamp=none`; four builds in a
  row then succeeded. Release builds still ask for a timestamp, which notarisation needs. The
  Designated Requirement is unchanged: the identifier and the Developer ID team.

### Notes for the next run

- A SwiftUI text field ignores an Accessibility write to its selection range, and focusing
  one selects all of its text. To place the caret, use the arrow keys.
- In AppleScript, `path`, `before`, `after` and `rows` are reserved inside a System Events
  `tell`. Using them as variable names fails with confusing errors.
- `screencapture` cannot capture a window from a process without Screen Recording permission.
  The Accessibility tree was enough without it.
- **Do not address a control by index through System Events when others share its name.**
  `UI element 12 of pane` is rewritten into a lookup by name, such as `menu button "More"`,
  which returns the first match. Both retracted findings above came from System Events, not
  from SignalLadder. Iterate over `UI elements of pane` instead, or use the raw
  Accessibility API.
- **System Events does not show every attribute.** Its `title` and `description` missed
  `AXDescription` on SwiftUI buttons. Before reporting that a control has no name, read its
  attributes with `AXUIElementCopyAttributeNames`.

## Speech latency (2026-09-25): hold one synthesizer, and speech is as quick as a sound

`docs/dev/spikes/speech-latency.swift` times `AVSpeechSynthesizer.write` without speaking
anything aloud. For each utterance it records the time to the first buffer, the silence at the
start of the audio (samples below −40 dBFS), and their sum: when sound would begin if buffers
were played as they arrive. Voices: Daniel (compact en-GB, the default for en-GB), Jamie
(enhanced en-GB), Eddy (Eloquence en-GB). Texts: a short `{app}: {title}` line and a long one.
The cold, warm and fresh runs were sequential, so none timed another. The idle row comes from a
rerun of one voice, one process at a time, with nothing else speaking. A first idle run is
superseded: it ran two voices side by side, 30 s apart, so most of its trials followed only about
30 s of quiet, whatever their label said.

| Situation | Audible after (median) | Worst | Trials |
|---|---|---|---|
| One synthesizer, held, back to back | 6–19 ms | 36 ms | 69 |
| One synthesizer, held, after 5, 15 or 30 min with nothing else speaking | 48 ms | 130 ms | 5 |
| A new synthesizer in a process that has already spoken | 32–125 ms | 131 ms | 24 |
| A new process, speech used elsewhere recently | 215–336 ms | 599 ms | 38 |
| A new process, the first speech after a long quiet spell | about 2.5 s | 2.55 s | 2 |

What decides it is the speech service (`SpeechSynthesisServerXPC`). It starts with a process's
first synthesizer and exits with that process. The first speech after a long quiet spell took
about 2.5 seconds both times: the day's first run, and a run after 20 minutes with no speech
service running at all. Straight afterwards, with the voice data cached, a new process took about
0.3 seconds. A synthesizer that is held keeps its service, and it was still warm after 30 minutes
of idle: 39 and 28 ms after 5 minutes, 48 and 130 ms after 15, 77 ms after 30.

- Once speech starts, it renders typically 24 to 170 times faster than real time (13 to 250 at
  the extremes, over 117 warm trials). Buffers can be played as they arrive, and playback never
  runs dry.
- Leading silence is 0–3 ms for all three voices, which adds nothing.
- Voice choice does not matter once warm. Eddy is quickest; the enhanced voice matches the
  compact one within a few milliseconds.

**For the speech milestone:**

1. **Hold one synthesizer for the app's lifetime.** Create it when the rules load and any rule
   speaks, and warm it with a silent render. Speech is then within tens of milliseconds of a
   sound.
2. **Never create one per alert.** That costs about 0.1 s in a process that has spoken before,
   and about 2.5 s for the first speech after a quiet spell.
3. **Play buffers as they arrive.** Waiting for the whole utterance adds its render time for
   nothing.

**Not measured:** idle beyond 30 minutes, and memory pressure. Either might make macOS reclaim a
held synthesizer's service. If that happens, the first alert afterwards takes 0.3–2.5 s. For a
rule with both a sound and speech, playing the sound first keeps the sound from ever waiting on
speech. Log each spoken alert's latency in the app, so that a real night of idle settles it.

## M4 groundwork (2026-09-25): App Nap, the panel, the hotkey and Shortcuts

§11 lists three assumptions for M4 to verify. Measured today, or ready to measure.

### App Nap did not delay a background app's timers, while the Mac was in use

`docs/dev/spikes/app-nap-timers.swift` runs as a minimal accessory app and fires a 30-second
repeating timer (tolerance 0) for 15 minutes, recording how late each fire is against its due
time. Three copies ran side by side, each launched in the background with `open -g`:

| Variant | Median lateness | Worst | Fires over 1 s late |
|---|---|---|---|
| A menu-bar icon, as SignalLadder has | 1.5 ms | 2.2 ms | 0 of 30 |
| B the same, holding `beginActivity(.userInitiated)` | 1.5 ms | 2.2 ms | 0 of 30 |
| C no icon and no windows, the case App Nap is meant for | 1.3 ms | 2.2 ms | 0 of 30 |

No copy was delayed, not even the one App Nap should have throttled. That first run had the user
at the Mac. Two longer runs, the same afternoon, covered the Mac left alone, with a sampler
recording every 30 s whether the screen was locked, the display asleep, and how long since the
last input:

| State | Fires, all variants | Median lateness | Worst | Over 1 s late |
|---|---|---|---|---|
| In use | 90 | 1.3–1.5 ms | 2.2 ms | 0 |
| Idle 2–3 hours, unlocked, display on | 465 | 1.1–1.5 ms | 3.5 ms | 0 |
| Locked, display asleep (27½ minutes) | 165 | 1.3–1.5 ms | 3.4 ms | 0 |

The display slept at exactly 9,000 s idle, its configured 150 minutes, and the screen locked with
it. Nothing else was holding the display awake.

**So on this Mac App Nap never delayed a 30-second timer in a background menu-bar app** — in use,
idle, or locked and dark, with or without the activity assertion, with or without a status item.
§11's worry does not hold here, and the assertion is not needed to keep repeats on time.

What the assertion is for, instead, is the other thing `.userInitiated` does: it holds
`PreventUserIdleSystemSleep`. This Mac has system sleep disabled (`pmset`: `sleep 0`), so that
was not exercised. On a Mac that does idle-sleep — a laptop, or any Mac with sleep enabled — a
sleeping Mac runs no timers at all, which is a far larger delay than App Nap ever produced here.
**The M4 plan should hold the assertion while an escalation is live for that reason**, say so, and
treat "does an escalation survive on a Mac with sleep enabled, and on battery" as the open
question in place of App Nap.

`.userInitiated` also holds a `PreventUserIdleSystemSleep` assertion (seen in `pmset -g
assertions`). Held while an escalation is live, as §5.15 proposes, the Mac will not idle-sleep
mid-escalation. That is probably right for an alarm, but it is a consequence, not a side note:
the M4 plan must say so.

### Shortcuts

`/usr/bin/shortcuts` is present and runs from the app's context without Apple Events. A shortcut
that does not exist fails in about 150 ms with exit code 1 and "Couldn't find shortcut", which is
easy to report as §5.16 requires. Running a real one needs a harmless test shortcut, made by
hand.

A real run, 2026-09-29, with a hand-made shortcut, "SignalLadder Test": Wait 5 seconds, then
count the characters of its input and output the count. Its input was a `0600` JSON file in a
`0700` directory, holding the four fields M4 sends, filled from the editor's made-up sample
notification.

| Run                                 | Exit | Returned after | What came back                                  |
| ----------------------------------- | ---- | -------------- | ----------------------------------------------- |
| By name, with `--output-path`       | 0    | 5.18 s         | `181` in the output file: the input's exact length |
| Misspelt name                       | 1    | 0.07 s         | "Couldn't find shortcut" on standard error       |
| By name, no `--output-path`         | 0    | 5.19 s         | the same `181`, on standard output instead       |

Three things follow for M4. `--input-path` delivers the file and the shortcut can read it.
`shortcuts run` does not return until the shortcut has finished — about 0.2 s of its own on top
of whatever the shortcut does — so waiting for it would hold Tier 4 for the shortcut's whole run,
and §5.16's "delivered at successful launch" needs the launch-grace race of the M4 plan's Ruling
19. And without `--output-path`, whatever the shortcut outputs arrives on standard output: a
shortcut that passed its input through would print notification content there, which is why the
plan sends standard output to `/dev/null`.

### The panel and the hotkey: both work, with no permission prompt

`docs/dev/spikes/alert-panel.swift` shows a borderless, non-activating `NSPanel` with

Checked by a person on 2026-09-29, macOS 26.7, with the level fix in place (window-server layer

## Live checks (2026-09-29): a banner that replaces another is never captured

**Fixed in #12, the same day,** apart from one gap noted under "Opening Notification Centre
replays its history" below. Capture now reads on layout changes and lets each banner element
through once; health re-checks as soon as what blocked a self-test clears; and `verify-live.sh`
checks that two banners 2 s apart are each captured once.

The M3d listening checks and the three system-setting checks, done by a person with the harness
reading the menu. Everything they were meant to check passed; two of them turned up bugs they were
not looking for.

### The bug: a second banner, while the first is on screen, is missed

The listening test posted five notifications from Script Editor. Four matched their rules and
sounded; the fifth, posted 4 s after the one before it, was never matched, and the sound it should
have made never played. Reproduced silently with two test banners 3 s apart, first with a tool that
polls Notification Centre's accessibility tree, then with one that registers the same observer
`AXBannerWatcher` does, plus the events it does not listen for. Both print text only when it carries
a test marker, so no real notification could appear in the output.

- **Nothing stacks.** The second banner replaces the first inside the same window, in the same
  `AXNotificationCenterBanner` position. Its fields read correctly ("SL-B second", two text
  children), so parsing is not the problem.
- **The replacement fires neither event capture listens for.** The first banner arrives with
  `AXWindowCreated`. The second produces only `AXLayoutChanged` (on the banner group and its scroll
  area) and `AXUIElementDestroyed` for the first banner's elements — no `AXWindowCreated`, no
  `AXWindowMoved`. `AXBannerWatcher` re-reads the tree only on those two, so the second banner is
  never read at all.
- **A self-test could fail the same way.** Nothing in the mechanism spares the app's own
  self-test: one arriving within a few seconds of another banner would be missed, and the menu
  would report "Cannot verify itself" with nothing wrong. This follows from the events above; it
  was not observed. A banner at 13:17:41, 3.3 s after a test banner, first looked like a case of it,
  but the log's request identifiers show it was the app's health alarm (`signalladder.health`), not
  a self-test (`SignalLadder canary …`) — every self-test during Do Not Disturb was held back by it,
  and the next one, at 13:20:57, passed.

What this means for an on-call Mac: a banner stays up about 5 s, and any notification arriving
while another is showing is lost. A burst of alerts during an incident sounds only the first.

**Why the fix is not just "listen for `AXLayoutChanged` too":** the same run shows it firing for the
first banner again 1.6 s and 2.2 s after it appeared, with nothing new on screen. Content dedupe
only covers 1.5 s, so re-reading on every layout change would record the first banner again and
sound its alert twice. Capture needs to know which banner it has already read — by the banner
element's identity, since the replacement is a new element (the old one's destruction is what
fires `AXUIElementDestroyed`) — and to read only banners it has not seen.

Cross-app replacement (a banner from one app replacing another's) was not tested: `osascript` posts
only as Script Editor. The single banner window makes it likely to behave the same.

| ----- | ------------------ | ------ |

| …and back on | Capture resumed in the same process (a test banner was caught) — no relaunch | ✅, but see below |

### Health does not re-check when the thing that blocked it clears

- **After Accessibility is granted again**, capture resumes — the observer survived — but no
  self-test runs. The menu went straight back to "Working — verified 20 min ago", quoting a check
  from before the outage. True this time; not proven.
- **After launching with its own banners switched off**, the app rightly skips its self-test —
  and schedules no retry, since only a failed self-test does. Once Desktop was ticked again the menu
  read "Checking…" for minutes, and would have until the regular 30-minute self-test. `HealthTitle`
  itself says "Checking…" must not imply a check that is not under way; here none was.

Both want the same thing: a self-test as soon as the blocking condition is seen to have cleared.

### Opening Notification Centre replays its history

Found while building the fix above, with the same marker-only tools. Opening Notification Centre
fires `AXWindowCreated` on the same window banners use, and its history items carry the same
subroles, so capture read every one of them as a fresh arrival — and a rule that matched an old
notification sounded again. It did this before any change of ours; it was just never looked for.

- **Items a minute or more old end with a time label** ("1m ago", "13m ago") as their last text
  child, which is not one of their description's fields. A live banner's last child always is.
- **Items under a minute old carry no label at all,** and look exactly like live banners.
- **A notification arriving while Notification Centre is open** appears at the top of the same
  list, with no label, and stays on screen as an ordinary banner once the panel closes.
- **The history panel's window is the banner window,** with the same title and size; the only
  difference found is that it is focused while open.

#12 skipped items with a time label, so history a minute old was no longer replayed — most of the
time. History under a minute old still was, which is the common case: an alert sounds, you open
Notification Centre to read it, and it sounds again.

### How the panel opens, and what fixed it

Traced event by event, printing text only for marked test notifications:

- **The label cannot be trusted even on old items.** An item read "19m ago", then had no label
  17 ms later, then had it again. #12 skipped labelled items without remembering them, so a read
  that caught one without its label captured it — a replay #12's own live check was lucky to miss.
- **The panel is recognisable.** It opens either in a new window (`AXWindowCreated`), or, when a
  banner is on screen, by turning that banner's window into the panel (`AXFocusedWindowChanged`,
  the live banner keeping its identity). Either way the window then has keyboard focus and holds
  the panel's own `AXMenuButton` beside the list. A window showing only banners had neither.
- **Everything is in place at once.** Every history item was present at the first event after the
  panel opened. In one run the panel was torn down and rebuilt 1.5 s later with new identities,
  which looks like a second opening.
- **Arrivals while it is open** appear inside the same list — once about 3 s after being posted,
  two at once, the newest at the top and the other merged into a stack as a new element.

- **Labels can vanish altogether.** On one read, most rows — some hours old — showed no label at
  all. So nothing about a row identifies history from before the app was running.

The fix, as it ended up:

- **When a window becomes the panel, everything in it is history,** remembered by element. It is
  the only evidence that covers rows from before the app was running.
- **A row appearing after that** is history if it carries a time label (scrolled into view), or
  if it replaces a captured element with the same text destroyed in the last 2 s — a stack laid out
  again as new elements. That evidence is single-use and short-lived because a first version that
  trusted any recently captured text set aside a genuine repeat, a second "Build failed", arriving
  while the panel was open. Otherwise the row has arrived while the panel is open, and is captured
  once a second read, at least 250 ms later — past the measured 220 ms flicker — still finds no
  evidence.
- **Outside the panel nothing is set aside.** An earlier version fell back on time labels there,
  and a live calendar reminder can end in something like "10:30".
- **The panel check** needs focus *and* the panel's own menu button as a direct child of the scroll
  area holding the list. Focus alone was seen to stay on after the panel closed.

Capture reads whole windows, once per burst of events, 50 ms after the first, and again when a row
needs its second read. Live, on a signed build: a fresh alert +1; opening Notification Centre with
it under a minute old +0, including an old notification of the app's own from before its launch,
which a content-only rule had replayed; an arrival while open +1; opening over a banner still on
screen +1 (the banner); two banners 2 s apart +2; `verify-live.sh` 13/13.

**One miss not explained.** During a harness run a persistent Outlook alert — Outlook withdrew an
earlier notification and presented this one, then withdrew it 12 s later — was never captured, and
nothing was logged. The build then running could have set it aside two ways: by the time-label
fallback outside the panel (a calendar reminder ending "Now" would match), or by taking its window
for the panel. Both were removed or tightened as above. Whether either was the cause is unknown;
an Outlook alert on screen is the next thing to look at, structure only.

### Persistent alerts, checked with Script Editor set to Persistent

- **A persistent alert's window is unfocused and has no menu button.** Hovering adds Close and
  Show buttons *inside* the alert element, and the window stays unfocused. So a live alert never
  looks like the panel. After the panel had been open, one window stayed focused without the menu
  button — focus alone would have taken it for the panel, and requiring both is what prevents that.
- **A second persistent alert from the same app was never captured.** It joins the first in an
  `AXNotificationCenterAlertStack` carrying the newest one's text, and that subrole was not in the
  allowlist. Teams alerts are persistent, so this was the second of any two Teams alerts close
  together. Now listed: alerts joining a stack are captured one each; opening Notification Centre
  over the stack adds nothing; an alert arriving while it is open is captured once.
- **Once, not reproduced:** a stack of seven persistent alerts from one app was laid out again as
  separate alerts — new elements — when another arrived while the panel was open, and those counted
  as arrivals (+3 for one alert). With a stack of two it did not happen. Like every replay, it errs
  towards repeating an alert rather than missing one.
- **By design, not observed: a miss at the moment the panel opens.** Everything a window holds when
  it becomes the panel is history, so a notification that arrives after the last read before the
  panel opened, and is already in the window at the first read of the panel, is set aside with it
  and never captured. No live check has caught one; it follows
  from the rule above. It is the one place the panel rule errs towards missing an alert, and the
  user docs say so.
