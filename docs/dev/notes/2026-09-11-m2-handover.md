# M2 handover — known issues carried forward from M1

**Date:** 2026-09-11
**M1 merged at:** `ed1dc02` on `master`

Everything here was found during M1, judged not to block it, and deliberately deferred. Recorded so none of it has to be rediscovered.

---

## Load-bearing — fix in M2

### 1. `AXElementNode` cannot distinguish "absent" from "failed"

`Sources/signalladder-probe/AXElementNode.swift` returns `nil` / `[]` for both "this attribute genuinely has no value" and "the read failed" — an AX timeout, an invalid element, a permission hiccup. With a 0.2s messaging timeout against a busy `notificationcenterui`, a transient failure is indistinguishable from "no banner here", and the tree walk quietly stops.

**Why this matters more than it looks:** the §9 canary does **not** catch it. The canary detects _systemic_ blindness — the whole pipeline being dead. This drops _individual_ notifications while health reads green. It is the spec's silent-blindness pattern one level down.

Fixing it means surfacing `AXError` through the `AccessibilityNode` protocol, which ripples into every conformer. That is why it was not done inside M1.

### 2. Dedupe must key on element identity, not content

The probe collapses repeat callbacks by keying on the description text within a 1.5s window. That cannot distinguish one banner re-firing `kAXWindowMoved` during animation from two genuinely distinct notifications carrying identical text — and two identical alerts from a noisy channel is exactly the traffic this product exists to handle.

M1 made every suppression **visible** on stderr so the probe's evidence stays trustworthy, but the heuristic itself is wrong for production.

A second-order consequence is already present: since a banner is now emitted when _either_ the description or the children have content, a banner with an empty description reaches dedupe with `rawText: ""`. Two distinct such banners collide on the key `""`, and the second is reported as a suppressed repeat. Visible, not silent — but wrong.

**Both close together** by keying on element identity, which needs identity exposed through `AccessibilityNode`.

## Dormant — these activate together when the app becomes a `.app` bundle

Fix as one change. Discovering them separately would look like two unrelated flakes rather than one predictable consequence of packaging.

### 3. The two re-attach signals trigger inconsistently

`AXBannerWatcher` has two detectors. The `DispatchSourceProcess` exit handler goes through `scheduleReattach()` and respects backoff; the `NSWorkspace` handler calls `attach()` directly and bypasses it.

Harmless today **only because** `NSWorkspace` notifications never fire in a non-GUI CLI process (see M1 findings, Finding 9). Inside a real `.app` bundle both will fire — producing redundant observer churn plus a delayed attach that tears down a freshly-healthy observer.

### 4. No cancellation token for pending `scheduleReattach` retries

A stale retry timer can fire after a successful attach and tear down a healthy observer to rebuild it, causing a brief capture gap. Idempotent, so wasteful rather than unsafe — but it compounds with issue 3 once both re-attach paths are live.

## Unverified — do not assume these work

- **Idle CPU** was never measured. The design is event-driven and should sit near zero, but that is reasoning, not observation.
- **Backoff reset across repeated restarts.** Verified across one restart; not across several consecutive ones.
- **The dedupe suppression path has never fired in the wild.** M1 proved it does not over-suppress; it did not prove it suppresses when it should.
- **Stacked banners were never observed.** `AXNotificationCenterBannerStack` / `AlertStack` handling — including deepest-match-wins — is exercised only by unit tests against fakes.
- **Focus-mode behaviour.** Whether banners are drawn at all during a Focus is unknown, and the spec flags it as a likely capture gap.
- **`INFocusStatusCenter` entitlement.** May require Apple approval, which would make the `focusActive` condition unbuildable rather than merely unreliable. Spec §11 schedules this spike for M2 precisely because it decides whether a whole condition type exists.
- **Whether the signed CLI binary holds its own TCC grant** or inherits the terminal's via responsible-process attribution. The shipping `.app` will hold its own identity; the probe may not. Relevant to M2's onboarding design.

## Environment notes

- `swift build` / `swift test` fail under the default Bash sandbox (`sandbox-exec: sandbox_apply: Operation not permitted`) — SwiftPM's own manifest sandboxing colliding with the outer one. Run with the sandbox override.
- Orphaned `codesign -d` processes can wedge and block all subsequent signature operations, including `swift test`. Symptom is commands hanging at 0% CPU. `pkill -9 -f "codesign -d"` clears it.
- Signing must use the Developer ID identity explicitly. Ad-hoc signing silently drops `--identifier`, degrading the Designated Requirement to a bare cdhash that changes every build — which kills the TCC grant on every rebuild.

## Added by M2a (2026-09-11)

### Closed by M2a
- Issue 3 (inconsistent re-attach triggering) and issue 4 (no retry cancellation token) are **fixed**. Both signals now route through one timer, and backoff grows per *failed attempt* rather than per signal — a bundled app fires three signals per restart, and the original code let each one push recovery further away.

### Still open, unchanged
- **Issue 1** — `AXElementNode` conflates "attribute absent" with "read failed". Still the highest-value fix for M2b: the canary detects *systemic* blindness, not individual dropped reads.
- **Issue 2** — dedup keys on content, not element identity. `CaptureDeduplicator` now exists in `NotificationCore` and is unit-tested, so the switch to identity keying lands in **one** place instead of two.

### New, deferred from M2a
| Where | Issue |
|---|---|
| `AppDelegate` | No live recovery from the untrusted-permission state — trust is checked once at launch, so granting permission leaves the app inert until relaunched. **This is exactly what M2b's onboarding must fix**; the spec already calls for polling trust after the prompt. |
| `AppDelegate.updateMenu` | Rebuilds the whole menu on every capture and allocates a `DateFormatter` per call. Adopting `NSMenuDelegate.menuNeedsUpdate(_:)` fixes both. |
| `AXBannerWatcher.attach()` | The cancellation after `reattachDelay = 1.0` is dead code — `detach()` at the top already cleared it. Harmless, but reads as a guard while providing nothing. |
| `AXBannerWatcher.observeWorkspace()` | Observer tokens are discarded and never removed, and `start()` has no re-entry guard. Single-call today. |
| `Scripts/make-app.sh` | A failing `mv` between `rm -rf "$APP"` and install could leave no bundle at all. Exits loudly; never leaves a silently-bad one. |
| `AppDelegate.openAccessibilitySettings()` | The macOS 14+ Settings URL is updated but **unverified by live testing** — it is the only escape hatch in the untrusted branch, so confirm it actually opens the right pane. |

### Verified working, do not re-litigate
- Capture, parsing, dedup, and re-attach all confirmed live in the bundled app, including across repeated `notificationcenterui` restarts with all three signals active.
- The bundled app holds its own Accessibility grant, separate from the CLI probe's.
- Idle CPU measured and acceptable.

### Structural note for M2b
`main.swift`'s top-level `let delegate` is what roots the object graph — `NSApplication.delegate` is a **weak** reference. If the delegate were constructed inside a function, the watcher and the unretained observer refcon pointing at it could be released early. Preserve that structure.
