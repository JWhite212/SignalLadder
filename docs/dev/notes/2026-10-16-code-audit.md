# Code audit — defects, waste and debt, and the train that clears them

**Date:** 2026-10-16
**Read at:** `982ed45`, with each item checked again on `efb499c` before it was written down here
**Status:** the train has run, on 2026-10-16. Every approved row is merged, R16 the structural car last, as #140. The merge of #142 put R16's old copy of `OnCallCheck` and `RuleReach` back at the end of `OnCall.swift`, and `main` did not build until #144 took it out on 2026-10-17. What is left is either blocked by pins (R13, X1 to X7, each filed), the owner's decision (B6, B7, I4) or a live check (B8, B9). The ledger is the contract for every pull request that follows from it, and each one links back here.

This note records a read of the whole package for what stands between it and code that is clean, free of repeated rules and easy to follow, and for defects found on the way. It ranks what was found, says how each finding was established, and lists what pins the code's current shape, so that a change can keep every test as it is. The test suite is the proof that behaviour did not move, so a test edited to let a refactor pass would rewrite the contract it claims to keep. Where a change cannot be made without editing a test, it is listed as blocked, not done quietly.

Every count below carries the command that produced it and the commit it was taken at. A count is true of that commit only. Whoever picks up an item re-runs its command on their own branch point and quotes the difference.

## How it was read

- Six read-only passes, each over one part of the package with nothing shared between them: the capture and rules path; escalation, health, on-call, snooze and setup; the app target with the audio, Shortcut and panel libraries; build, scripts, configuration and the test suite as code; then a second pass over the code the latest fixes changed, and one over the functions with the most branches. Each finding had to name what pins it, show its evidence, and say which of five kinds it is.
- A mechanical pass beside them, for signal, not verdicts: `swiftlint` with a configuration of its own outside the repo (cyclomatic complexity 12, function body 60 lines, type body 400, file 600, force-try, force-cast), a token-window search for repeated code, and a count of declarations named only once.
- The baseline at `982ed45`, Xcode 27.1 on macOS 27.2: `swift build --build-tests -Xswiftc -warnings-as-errors` clean, and `swift test --skip-build` 2339 tests with no failure (26 Shortcut, 19 storage, 2206 core, 15 panel, 73 audio).
- Each defect was confirmed by reading the code, and where it could be, by running it: a scratch program over copies of the pure sources, or the new test against the old code.

## Verdict on the architecture

The architecture is sound, and the debt is small and local.

- **Decisions are pure, and the boundary holds.** `NotificationCore` imports Foundation and CryptoKit and nothing else, and `PurityTests` holds it there. The libraries that touch the system depend on the core or on nothing, and the app depends on all of them. There is no cycle, and no third-party package.
- **The app target is thin, with one exception of size.** `AppDelegate.swift` holds 60 stored properties and 57 functions, and its longest function is 41 lines of code. It is large by responsibility, not by depth, so splitting a function in place buys little. Splitting the file is pinned (see Blocked).
- **What the app target cannot test, its wiring tests read as text.** `grep -rho '"AppDelegate.swift"' Tests | wc -l` gave 88 at `efb499c`, across 11 files (`grep -rl … | wc -l`). That makes every textual change to the app target a test edit, and that is the price of an untested target, not a fault in it.
- **There is very little copied code.** The token-window search found no repeat of 70 tokens and three of 35 or more (`python3 -I dup.py Sources 35`). What repeats is small rules, written two to five times, and a few long functions that mix steps.
- **The complexity is mostly by design.** Of the 16 functions over the thresholds, the eight with the most branches are exhaustive `switch` statements with no `default`, which the project prefers so that a new case has to be decided. With `ignores_case_statements: true`, none of those eight is flagged.

So that the next read does not open them again:

- **Pure forwarding wrappers in the core**, such as `OnCallCheck.shouldOpenWindow` and `SetupPlan.promptsAtLaunch`, are the seam where the core says and the app carries out, each held by a wiring test.

- **Frozen preset timings, raw strings that must not follow case names, and an enum with one case** are each explained where they are.

- **`OnCallText.noSoundOrShortcut`** says a match will only show the panel, which over-claims for an enabled silent rule with no ladder; it is the plan's Ruling 9 text, so it is the owner's to change.
- **Test seams in production code**: `AlertPlayer`'s offline mode, `trackedCount`, `bookkeeping(of:)` and the panel's drawn lines are how the audio, escalation and panel are tested.
- **One `AccessibilityNode` implementation** in production is the purity seam.
- **The five preference stores** differ in shape, and each is the only writer of its key.
- **Two `LoginItem.status` reads per menu opening** are what Ruling 9 asks for, at a cost the owner measured.
- **Wall-clock assertions** in three tests, with wide margins.
- **`bounded()` and `die()`** copied once between two standalone scripts.
- **A distinct notification whose text contains an earlier one's**, within 1.5 s and matching the same rule, plays nothing of its own, as M3a Ruling 10's amendment says.
- **A page that fails fast on waking** is not tried again, as M4 Ruling 14's amendment says.
- **`HealthEvaluator.evaluate`** reads as one ladder whose order is its meaning, and splitting it would spread that order over three functions.

## The train

One pull request each, in this order. A car branches from `main` as it is when the car starts, finds its code by what it says, not by the line numbers here, and runs its row's command again before it plans anything.

1. **The bug batch**: B1 to B5, each with a test that fails without it.
2. **The guard fix whose tests hold the bug**: B12, with each rewritten guard shown to fail on a violation put in on purpose and then taken out.
3. **Build and configuration**: B10, B11, I1 to I3.
4. **Measured waste**: P1.
5. **The refactors**: R1 to R15, in any order. The suite passes unchanged, or the car stops.
6. **The structural car, last**: R16.

A car stops, and says so on its pull request, when the code it cites has already changed, when a new pin appears, when it needs a file outside its scope, or when a test would have to be edited.

## What this audit learned

- **A compiler warning is a pin.** R13 was to stop two functions returning a value every caller drops with `_ =`. That was judged safe because `_ = f()` compiles when `f` returns nothing, but Swift 6.4 warns that it is redundant. With warnings as errors, every caller would have to change, and a wiring test holds those lines word for word. It was built, failed and was put back. Only building it showed this.
- **A speed-up can trade away a reported failure.** Keeping the voice list made a spoken alert 45 ms sooner and, in one rare case, silent where it had been loud about failing. A read of the merged diff found it, not the tests, since no test can uninstall a voice.
- **The structural car was cheap because the pins are by name.** The tests and the live check that read the source by file read named constants. So the types around those constants could move to new files with no test edited, as long as each constant stayed in the file it is read from.
- **A car stacked on another is rebased, not merged, once the first lands.** #135 was built on #134's branch. When #134 was merged as a rebase, its commit came back with a new hash, and a rebase of #135 onto `main` dropped the old one.
