# M3d: Alerts That Speak — Implementation Plan

> **Execution:** each task is implemented with its tests, committed behind a gate (full suite green at the expected count, zero build warnings), and then independently reviewed against the requirements below.

**Goal:** Let a rule speak a short line built from the notification that matched it — on its own, or alongside its sound — level-matched and reported as honestly as a sound already is, without ever making a sound wait on speech or a spoken sentence leave memory.

**Architecture:** The rule format gains a `.speak` alert and a combined `.soundAndSpeak` alert, and moves to version 3. Template substitution, speech validation and every new line of wording stay pure code in `NotificationCore`, beside the sound equivalents they extend. Playback stays inside `AlertAudio`: the existing engine gains a second player node at speech's own format and a single `AVSpeechSynthesizer` held for the app's lifetime, still proven entirely by rendering the graph offline — nothing in this milestone makes a sound in a test. Starting *any* alert — sound, speech, or both together — claims the engine's shared interruption state exactly once, through one internal entry point, so a combined alert cannot cut off the very sound it just started. `PurityTests` is extended to actually forbid `AVFoundation` in `NotificationCore`, which it does not today. The app target wires three injected closures and extends the rule editor already built in M3c. No new library target, and no Settings window.

**Tech Stack:** Swift 5.9, AVFoundation (`AVSpeechSynthesizer`, `AVAudioMixerNode`), AudioToolbox, CoreAudio (read-only output state), AppKit, XCTest.

**Spec:** `docs/dev/specs/2026-09-11-macos-notification-router-design.md` — §2.1 privacy, §5.8 alert actions, §5.9 SpeechEngine, §5.15 serialised audio, §5.16 audio engine, §6 persistence, §7.2 Inspector, §7.4 rule editor, §7.5 settings (voice picker only — no Settings window exists yet, and none is built here), §12 milestones, §13 out of scope (Siri voices), §14 defaults (speech template).

**Measured groundwork:** `docs/dev/notes/2026-09-11-m1-findings.md`, sections "Speech (§5.9), rendered without being spoken" and "Speech latency (2026-09-25)"; `docs/dev/spikes/speech-render.swift` and `speech-latency.swift`.

## Global Constraints

- **Notification content is never written to disk, logged, or transmitted** (§2.1). A spoken sentence is built from a notification's title and body, so it is exactly as sensitive as they are: it may live in memory, precisely where the rest of a captured notification already lives, and nowhere else.
- `NotificationCore` imports no UI or permission-bearing framework and touches no file, network, or AVFoundation API. The AVFoundation half of that is not enforced today — `PurityTests.testCoreHasNoForbiddenImports`'s forbidden list is `["ApplicationServices", "AppKit", "Cocoa", "Carbon", "UserNotifications"]`, and nothing stops a stray `import AVFoundation` in a new file. Task 1 adds it. The template, its substitution and every validation rule live in `NotificationCore`; `AVSpeechSynthesizer` does not.
- Nothing may claim more than was established. Spoken is not heard, exactly as played is not heard.
- **Two alarms at once is noise, not information** (§5.15). A new alert interrupts whatever the last one was doing, on every node it used, whichever modality the new alert itself uses — and it does so once, not once per modality it happens to combine.
- macOS 14.0 floor; event-driven; near-zero idle CPU. A synthesiser, and the system service behind it, is created only once a loaded rule actually speaks — never speculatively, never at launch, and never in a way that makes launch itself wait on it.

## Rulings

**1. A rule's alert may be a sound, speech, or both — never mutually exclusive by construction.** The measured findings assume exactly this case ("if a rule has both a sound and speech, the sound must never wait on speech"), and it earns its place on its own merits: a sound is heard across a room and says only "something matched"; speech says which one, useful the moment you are not looking at the screen. `AlertAction` gains `.speak(SpeechAction)` and `.soundAndSpeak(soundName:, soundGainDB:, speech:)` alongside the existing `.sound` and `.silent`. This is a deliberate departure from §5.8's original enum, where sound and speech are alternatives inside one escalation tier; the implemented `Rule` has no tiers to put them in, and combining them in one alert is the smaller, more useful change.

**2. Speech requires format version 3, gated exactly as alerts required version 2 — and validated from whichever case actually carries a sound name or a voice identifier, not only `.sound`.** A `.speak`/`.soundAndSpeak` alert in a file below version 3 is a problem naming the rule and the fix, worded like the existing "alerts need `\"version\": 2`" message. `RuleSetCodec.reasons(for:fileVersion:sounds:)` checks a sound name today with `if case .sound(let name, _)? = rule.alert` (line 97) — a pattern that would never fire for `.soundAndSpeak`, silently skipping the sound-name check on exactly the rules ruling 1 just introduced. `AlertAction` gains small computed accessors (`soundName`, `speechVoiceIdentifier`) that return a value for whichever case carries one, and `reasons(for:…)` is rewritten against those instead of a single `case .sound` match, so a misspelt sound name is caught on a `.soundAndSpeak` rule exactly as it is on a `.sound` one. Today's strict unknown-key rejection would already refuse an unrecognised `"speak"` key with a generic error — a safety net, not a substitute for a message that says what actually went wrong.

**3. Speech's own gain reuses `AlertAction.gainRange` (−40…+12 dB) unchanged.** Speech measures 10 dB hotter than most sounds at the same setting (−1.32 dBFS peak against −15 to −5 for sounds), but that gap is exactly what peak normalisation already absorbs — the same mechanism, unchanged, that makes "gain 0" mean the same loudness for every sound. The rule's `gainDB` is what the user asks for on top of that, and means the same thing for speech as it does for a sound.

**4. Speech is level-matched per voice from one silent calibration render, and until that render is in, it errs quiet.** Measuring a whole utterance before playing it would bring back the render-then-play delay this milestone exists to avoid ("play buffers as they arrive"). So each voice's peak is measured once, from a fixed non-notification phrase, in the background (ruling 6). An alert that needs a voice whose calibration has not arrived yet does not wait for it: it plays as if the voice peaked at 0 dBFS. Against `Loudness.targetPeakDBFS` (−1) and the measured −1.3 dBFS, that is at most about a decibel quieter than calibrated, and never louder, and the limiter bounds it either way.

**5. Sound and speech each get their own `AVAudioPlayerNode` and `AVAudioUnitEQ`, merged through a new `AVAudioMixerNode` before the one existing limiter.** Speech's buffers are float32, 22,050 Hz, mono — not the sound path's 48 kHz stereo — and `AVAudioUnitEQ`/`AVAudioUnitEffect` are single-input nodes, so a second producer cannot feed the existing EQ directly. A mixer node upstream of the limiter lets sound and speech carry independent gains (needed when both fire from one rule, at different chosen levels) while still sharing one limiter and one path to `mainMixerNode` — one safety net, not two, and one place gain can go wrong instead of two.

**6. The one held `AVSpeechSynthesizer` is created, warmed and calibrated asynchronously, and nothing in the app ever waits on it or pumps the run loop for it.** `write(_:toBufferCallback:)` delivers its buffers on the main run loop, and the first speech after a quiet spell takes up to ~2.5 s. `RuleStore.reload()` runs synchronously at launch, on Reload Rules and on every save, so it cannot wait that long; and `speak()` runs inside the Accessibility capture callback, where pumping a nested run loop could deliver other capture callbacks and timers mid-alert and re-enter the pipeline. So `prepareSpeech(voiceIdentifier:)` is `async`, bridging the callback with a continuation, and `reload()` starts it in a `Task` and returns. An alert, or Test Speech, for a voice not yet warmed simply calls `write()` at once: the service starts on that call, which costs no more than waiting would have, and the voice plays at the default level (ruling 4) until its calibration arrives.

**7. Preparing a voice a second time is a no-op, and preparing one already in progress waits for the first.** Rules reload on every save and every hand edit; recreating the synthesiser or re-calibrating a voice on each of those would repay the cold start that holding it for the app's lifetime exists to avoid. The rule editor's picker prepares a voice when it is chosen, so Test Speech usually finds it warm.

**8. Starting an alert claims the shared interruption state exactly once, however many nodes that one alert uses.** Today's `start()` (`AlertPlayer.swift:183–209`) bumps `generation`, unconditionally stops the player, and schedules a buffer, all inside one call — and every public entry point (`play`, `testSound`) calls it once per alert. A `.soundAndSpeak` alert built by calling a sound-shaped entry point and a speech-shaped entry point back to back — each independently claiming "an alert is starting, stop everything" — would have the second call's unconditional stop cut off the sound the first call had just scheduled, moments earlier, under its own generation: the opposite of what ruling 9 requires. So the two are never composed that way. `AlertPlayer` gains a private `beginAlert()` that stops both player nodes, bumps `generation` once, starts the engine if needed, and returns the new generation; every public entry point — the existing `play`/`testSound`, the new `speak`/`testSpeech`, and the new combined `outcome(ofPlayingAndSpeaking:…)` — calls it exactly once, and a combined alert's sound-scheduling and speech-request both run under that single returned generation rather than each claiming their own. `isPlayingAlert` clears only once every node the current generation actually used has reported its own completion.

**9. A new alert's sound is scheduled before its speech is even requested — a call order inside one `beginAlert()`-claimed generation, not two separately-interrupting calls.** The combined entry point calls `beginAlert()` once, schedules the sound buffer, and only then calls `write(_:toBufferCallback:)` for speech — both synchronous, neither waiting for playback or rendering to finish, so the sound is audibly under way before speech synthesis is so much as asked for. Sound and speech are attempted independently after that: a failure in one does not skip the other, so a rule whose sound plays but whose voice is no longer installed still speaks nothing, but still sounds.

**10. A cancelled utterance's buffers are discarded by checking `generation`, never by trusting `stopSpeaking`'s callback behaviour or the timing between calling it and the next `write`.** Two things are unverified, not one: whether `stopSpeaking(at: .immediate)` still delivers a clean, empty terminal buffer afterwards, and whether it takes full effect before the very next `write()` call is issued rather than briefly overlapping it — neither spike exercises interruption at all, only sequential calls issued after a previous utterance had already finished. `stopSpeaking` is still called, as a courtesy, before requesting new speech. Correctness comes from the same generation check every buffer is already subject to: a buffer arriving for a generation that is no longer current is dropped, whatever produced it and whatever state the synthesiser was actually in when it arrived. Task 3's tests and Task 6's live check prove the visible symptom — clean cut, no overlap, no stray audio — not the synthesiser's internal guarantee, which stays an open question the same way the >30-minute idle one does.

**11. A voice identifier is validated at rule load by checking membership, not by attempting anything.** `RuleSetCodec.SoundCheck` pairs `available: Set<String>?` with `unplayable: ((String) -> String?)?`, because a sound file genuinely can fail to decode, be silent, or be too long — real failure modes discovered by attempting to prepare it. A voice identifier has no equivalent: across every trial in the measured findings, an installed voice failed to render in none of them, only more slowly in some. So the sibling `VoiceCheck` carries only `available: Set<String>?`, built from `AVSpeechSynthesisVoice.speechVoices()`'s identifiers — no `unusable` closure, and nothing that calls `prepareSpeech` from load-time validation. A rule naming an uninstalled voice is still reported by name at load, not discovered as silence at the incident; it is simply a cheaper check than sound's, because there is less to check.

**12. The picker lists every voice `AVSpeechSynthesisVoice.speechVoices()` returns, unfiltered by language, with a link to System Settings for more.** §5.9's Siri constraint is satisfied by construction: `speechVoices()` never returns a Siri voice, so nothing needs to filter one out, and nothing in the picker implies one is selectable. Filtering by the system's own language is deliberately not done either: `{app}` and `{title}` come from whatever notification matched, in whatever language that app and the user's Mac produced it in, so a picker that only offered voices for the system's language would silently be the wrong tool for a non-English banner on an English-language Mac. No API triggers a download, so the picker shows installed voices only and links to System Settings › Accessibility › Spoken Content — its precise deep-link identifier confirmed by hand during implementation, the way M3b's own deep links (Notifications, Focus) were confirmed as a human check rather than guessed at in the plan.

**13. The spoken sentence is never shown in the status-bar menu — only the Inspector shows it, and only there.** The menu today shows a sound's library name and nothing of a notification's content; showing a rendered `{app}: {title}` sentence at a glance, in meetings, on a shared screen, would be a materially larger and unearned privacy surface. `InspectorRowText.alert(_:)` — reused by both — never includes the sentence; the Inspector alone reads it directly off `AlertOutcome`, next to the raw banner text it already shows behind disclosure.

**14. A sound-and-speech alert's partial failure is reported as `.failed`, naming which half failed and whether the other succeeded — and the reason is composed in full where the failure happens, not assembled by the renderer.** `InspectorRowText.alert(_:)` renders every `.failed(reason)` today as `"Could not play: \(reason)"` (`InspectorEntry.swift:211`) — a prefix hardcoded at render time, not part of the reason string. Reusing `.failed(String)` unchanged for a speech-only or combined failure would run every reason through that same "Could not play:" prefix regardless of what actually failed: a lone speech failure would read "Could not play: voice … is not installed" for a rule that never touched a sound, and a sound-succeeded-speech-failed rule would read "Could not play: played Glass, but could not speak: …" — asserting and denying that the sound played in the same sentence. So the prefix moves to where each failure is actually produced: `AlertPlayer.outcome(ofPlaying:…)` builds `"Could not play: …"` itself, the new `outcome(ofSpeaking:…)` builds `"Could not speak: …"`, and the new `outcome(ofPlayingAndSpeaking:…)` builds whichever full sentence fits — "Could not speak: …" when only speech failed, "Played Glass, but could not speak: …" when speech failed after sound succeeded, or "Could not play: …" when sound itself failed. `InspectorRowText.alert(_:)`'s `.failed` case becomes a pass-through. `AlertOutcome` stays one case per shape of thing that happened (`.played`, `.spoke`, `.playedAndSpoke`, `.failed`), matching every existing outcome, rather than a matrix of independent per-modality success flags — for one milestone whose job is "speech as an alert action, not escalation," a fully-composed `.failed` reason says everything a rule author needs.

**15. Latency is logged through a function that cannot be handed a rendered sentence, because it has no parameter that could hold one.** Per the findings note's own instruction: log each spoken alert's latency, never its text, so a real night of idle settles whether macOS ever reclaims a long-held synthesiser beyond the measured 30 minutes. The time from `write` to the first non-empty buffer, and whether this call created or calibrated the synthesiser, are logged via `os_log`, under the same subsystem and category convention `AXBannerWatcher.log` already uses (`com.jamiewhite.signalladder`, a new `"speech"` category) — but not its signature. `AXBannerWatcher.log(_ message: String)` is a free-text sink whose safety depends entirely on the caller never passing it notification content; that is precisely the kind of mistake a speech code path, sitting right next to the rendered sentence, must not be able to make by a moment's inattention. The new function is `logSpeechLatency(_ seconds: Double, freshlyPrepared: Bool)` — it formats its own `os_log` call internally, and has no `String` parameter for a caller to misuse.

**16. The rule editor's alert kind gains a fourth option, Speech, and choosing Sound reveals an "Also speak it" toggle — and either path needs a default voice the instant it is chosen, the way choosing Sound already defaults to "Glass," or the first available sound.** Toggling it on, or choosing Speech directly, adds a `SpeechAction` defaulting its `voiceIdentifier` to the system's default voice (`AVSpeechSynthesisVoice(language: nil)`) when that voice is among the installed ones the picker offers, otherwise the first available voice — an empty identifier would itself be a load-time problem under ruling 11, so one is never left unset. Toggling "Also speak it" off reverts to plain `.sound` without discarding the entered speech fields, which are held in the view's own state so a toggle-off-then-on restores them — the same care M3c's editor already takes not to lose what the user typed on a structural change.

**17. Rate and pitch are edited in their spec units — 0…1 and 0.5…2 — each shown numerically, with the defaults (0.5, 1.0) pre-selected.** No friendlier unit is established for either, the way whole decibels were established for gain; introducing one here would be a guess this milestone does not need to make.

**18. A rendered spoken sentence is capped at a fixed length, whatever the template names.** The spec's own reasoning for the default template — "a 40-second recitation of a Teams thread is not an alert" — is a reason the default omits `{body}`, not a bound on what a hand-written template can do: a custom template naming `{body}`, or simply a long real `{title}` (banners are not guaranteed short), reproduces the exact failure the default was chosen to avoid, by a different route. `SpeechAction.rendered(for:)` truncates its output at 240 characters with a trailing "…" — a number chosen for proportion, not measured against actual spoken duration, since nothing in this milestone's groundwork measured that ratio. The cap applies regardless of which placeholders are used, so it needs no separate "problem" at rule-load time: length depends on the notification, not the rule.

## Task 1: Speech in the rule format (version 3)

**Files:** `Sources/NotificationCore/Rule.swift`, `Sources/NotificationCore/SpeechAction.swift` (new), `Sources/NotificationCore/RuleSetCodec.swift`, `Sources/NotificationCore/RulesDocument.swift`, `Sources/NotificationCore/DryRun.swift`, `Tests/NotificationCoreTests/PurityTests.swift`, `Tests/NotificationCoreTests/…`

- `AlertAction` gains `.speak(SpeechAction)` and `.soundAndSpeak(soundName: String, soundGainDB: Double, speech: SpeechAction)`. `.sound` and `.silent` are untouched. Two small computed accessors, `AlertAction.soundName: String?` and `AlertAction.speechVoiceIdentifier: String?`, return a value for whichever case carries one — the basis for ruling 2's fix.
- `SpeechAction`: `voiceIdentifier: String`, `template: String` (defaults to `"{app}: {title}"` when the key is omitted — §14), `rate: Float` (0…1, default 0.5), `pitchMultiplier: Float` (0.5…2, default 1.0), `gainDB: Double` (default 0, `AlertAction.gainRange`, ruling 3).
- `SpeechAction.rendered(for:)`: pure substitution of `{app}`, `{title}`, `{body}` against a `CapturedNotification`, in one pass, then truncated to 240 characters with a trailing "…" (ruling 18). Tested with developer-authored, redacted fixtures (§10.1) — never real captured content — including one long enough to exercise the cap.
- JSON: the alert object's existing `"sound"`/`"gainDB"` keys may be joined by an optional `"speak"` object — `{"voice": "…", "template": "…", "rate": 0.5, "pitch": 1.0, "gainDB": 0}` — every key but `"voice"` optional. `"speak"` alone decodes to `.speak`; `"sound"` and `"speak"` together decode to `.soundAndSpeak`; a top-level `"gainDB"` with no `"sound"` is an error naming the mistake ("gainDB with no sound to apply it to"). Unknown keys are rejected at both levels, the same mechanism as today.
- `currentVersion` is 3. A `.speak`/`.soundAndSpeak` alert in a file below version 3 is a problem naming the rule, worded like the existing version-2 gate (ruling 2). `version(for rules:)` returns 3 when any rule speaks, 2 when any has an alert but none speaks, 1 otherwise — the lowest version that can hold the file, unchanged in spirit.
- `problems(in:)` gains: an empty template; a `{placeholder}` in the template that is not `app`, `title` or `body`; rate or pitch outside their ranges; an empty voice identifier. Speech's gain reuses the existing gain-range check. No length check here (ruling 18): a template's length is not a rule's length.
- `RuleSetCodec.SoundCheck` gets a sibling `VoiceCheck(available: Set<String>?)` — no `unusable` closure (ruling 11). `reasons(for:fileVersion:sounds:voices:)` is rewritten to read `rule.alert.soundName`/`rule.alert.speechVoiceIdentifier` rather than pattern-matching `.sound` alone, so a `.soundAndSpeak` rule's sound name is checked exactly as a `.sound` rule's is (ruling 2). `RulesDocument.problems(in:sounds:voices:)` and `DryRun.report(…sounds:voices:)` widen the same way `sounds:` already threads through them. `RuleStoreStatus.load` gains `availableVoices: Set<String>?`, with no default, so the app cannot forget to supply it.
- `Rule.playsSound` is renamed `Rule.alertsAloud`, true for `.sound`, `.speak` and `.soundAndSpeak` alike (not `.silent` or nil) — the rename forces both of its two call sites to be revisited, rather than silently broadening a property whose old name would then be wrong.
- `PurityTests.testCoreHasNoForbiddenImports`'s forbidden list gains `"AVFoundation"` and `"Speech"`. It forbids nothing today that would stop a stray import in `SpeechAction.swift` or anywhere else in `NotificationCore` — this closes that gap rather than assuming it was already closed.
- Tests: every new JSON shape decodes and round-trips; an unknown key inside `"speak"` is rejected by name; a version-2 file with a `"speak"` key is refused, naming the fix; `"gainDB"` with no `"sound"` errors; template placeholder scanning catches an unrecognised token; rate and pitch bounds are enforced like gain's; `reasons(for:…)` reports an unavailable sound name on a `.soundAndSpeak` rule, not only on a `.sound` one; `rendered(for:)` truncates a long substitution and leaves a short one untouched.

## Task 2: The audio graph gains a speech path

**Files:** `Sources/AlertAudio/AlertPlayer.swift`, `Tests/AlertAudioTests/AlertPlayerTests.swift`

- A second `AVAudioPlayerNode` (`speechPlayer`) and `AVAudioUnitEQ` (`speechEQ`), attached and connected at speech's own format — float32, 22,050 Hz, mono, not `Self.format`. A new `AVAudioMixerNode` takes both EQs' output and feeds the existing limiter, which still feeds `mainMixerNode` (ruling 5). Nothing about the sound path's own format, cache or conversion changes.
- A private `beginAlert() -> Int`: stops both player nodes unconditionally, starts the engine if it is not running, bumps `generation` once, and returns the new value. Today's `start()` — the sole engine for `play`/`testSound` — is refactored to call it instead of bumping `generation` and stopping the player inline; behaviour for a sound-only alert is unchanged (still the existing tests), but a sound alert now also silences speech, and vice versa, because both entry points route through the one shared method (ruling 8).
- `isPlayingAlert` clears only once every node the current generation actually used has reported completion — tracked as a small outstanding-count per generation rather than a single flag, since a combined alert has two things that must each finish before the alert is over.
- No `AVSpeechSynthesizer` yet — this task proves the graph and the shared interruption machinery alone, scheduling synthetic buffers directly onto `speechPlayer` (and the existing sound buffer onto `player`), so it stays fast and deterministic and needs no real voice.
- Tests, all offline (`renderOffline`, reading the merged output as today): a sound-only play behaves exactly as before Task 2 (regression, existing tests unchanged); a synthetic buffer scheduled on `speechPlayer` reaches the limiter's output; sound and speech playing together does not exceed the limiter's ceiling any more than sound alone does; a new alert on either node silences whatever the other node was doing; scheduling a synthetic sound buffer and a synthetic speech buffer under one `beginAlert()` generation and then calling `beginAlert()` again mid-playback cuts off both — proving ruling 8 at the graph level, before Task 3 gives it a real synthesiser to drive.

## Task 3: The held synthesiser

**Files:** `Sources/AlertAudio/AlertPlayer.swift`, `Tests/AlertAudioTests/AlertPlayerTests.swift`

- `prepareSpeech(voiceIdentifier:) async throws`: creates the one `AVSpeechSynthesizer` if it does not exist yet, then calibrates the named voice if it has not been calibrated yet, by rendering a fixed, non-notification phrase through `write(_:toBufferCallback:)`, discarding the audio and keeping its measured peak. The callback is bridged with a checked continuation; nothing blocks or pumps the main run loop (ruling 6). A second call for a calibrated voice returns at once; a call for a voice being calibrated awaits the calibration already running (ruling 7).
- `RuleStore.reload()` (Task 4) starts `prepareSpeech` for each speaking voice in a `Task` and returns; `speak`/`testSpeech`/`outcome(ofPlayingAndSpeaking:…)` never await it. A voice not yet calibrated plays at the default level (ruling 4).
- `speak(_:voiceIdentifier:rate:pitchMultiplier:ruleGainDB:) throws -> SpeechReport` and `testSpeech(…)`, mirroring `play`/`testSound`: each calls `beginAlert()` once, then requests `write(_:toBufferCallback:)` at once, at the voice's calibrated level or the default one (ruling 4), and starts its calibration if none has been started. `Failure.alertPlaying` while a real alert plays, exactly as `testSound` already enforces. `SpeechReport` carries a resolved `voiceName`, the applied gain, and `OutputState`, the way `Report` does for a sound.
- `outcome(ofPlayingAndSpeaking: soundName:, soundGainDB:, text:, voiceIdentifier:, rate:, pitchMultiplier:, speechGainDB:) -> AlertOutcome`: calls `beginAlert()` once, then schedules the sound buffer, then requests speech (ruling 9) — both attempted independently, each failure caught rather than aborting the other (ruling 9), and the two results combined into `.playedAndSpoke` or a fully-composed `.failed` (ruling 14). This is the only entry point `.soundAndSpeak` alerts use; nothing composes `play` and `speak` as two separate calls.
- Buffers arrive on the callback (main thread, per the spike) and are scheduled on `speechPlayer` only when `generation` still matches the play that requested them; a stale generation's buffers are dropped, cancelled or not (ruling 10). `stopSpeaking(at: .immediate)` is still called on interruption, as a courtesy, before the next `write` is requested.
- `Failure.voiceNotFound(String)` added, described the same way `soundNotFound` is.
- Latency: `logSpeechLatency(_ seconds: Double, freshlyPrepared: Bool)` is called with the time from `write` to the first non-empty buffer and whether this call created or calibrated the synthesiser — nothing else, by construction (ruling 15).
- `outcome(ofSpeaking:voiceIdentifier:rate:pitchMultiplier:ruleGainDB:) -> AlertOutcome`, mirroring `outcome(ofPlaying:)`: never throws, turns a thrown `Failure` into `.failed("Could not speak: \(error)")` (ruling 14). `outcome(ofPlaying:)` itself is updated to build `.failed("Could not play: \(error)")` rather than the bare `String(describing: error))` it returns today, moving the prefix out of `InspectorRowText.alert(_:)` (ruling 14) — the rendered menu and Inspector text for an existing sound failure is unchanged, only where the sentence is assembled.
- Tests, all offline: a real, short, fixed phrase renders through a real, installed voice and its buffers reach the offline output at roughly the calibrated peak — nothing reaches a speaker, exactly as the spike found `write` needs no permission and makes none. Tests wait with an `XCTestExpectation` or an `async` test, never by blocking main: the callback arrives on the main run loop, and blocking it deadlocks (both spikes say so). `prepareSpeech` called twice for the same voice does not repeat the calibration render (an injected, counted factory or an identity check). An unknown voice identifier throws `.voiceNotFound` before any buffer is requested. `testSpeech` is refused while `isPlayingAlert`, and a real alert interrupts a test speech, exactly as sound's Task 5 (M3c) already proved for sound. `outcome(ofPlayingAndSpeaking:…)` with a real sound and a real short phrase reaches the offline output with both present under one generation, and a second call to `play`/`speak`/`outcome(ofPlayingAndSpeaking:…)` made while the first is still going leaves only the second's audio in the render — proving ruling 8's fix with the real synthesiser, not just Task 2's synthetic buffers. A `speak` for a voice never prepared plays at once at the default level, and a later `speak` for the same voice, once calibration has finished, plays at the calibrated level (rulings 4 and 6).

## Task 4: A match speaks

**Files:** `Sources/NotificationCore/CapturePipeline.swift`, `Sources/NotificationCore/InspectorEntry.swift`, `Sources/NotificationCore/AlertMenuText.swift`, `Sources/NotificationCore/MuteWalkthrough.swift`, `Sources/SignalLadder/CaptureController.swift`, `Sources/SignalLadder/AppDelegate.swift`, `Sources/SignalLadder/RuleStore.swift`, `Tests/NotificationCoreTests/AlertOutcomeTests.swift`, tests

- Three injected closures, alongside the existing `SoundPlayer`: `SpeechPlayer = (_ text: String, _ voiceIdentifier: String, _ rate: Float, _ pitchMultiplier: Float, _ gainDB: Double) -> AlertOutcome` and `SoundAndSpeechPlayer = (_ soundName: String, _ soundGainDB: Double, _ text: String, _ voiceIdentifier: String, _ rate: Float, _ pitchMultiplier: Float, _ speechGainDB: Double) -> AlertOutcome`, both required at `CapturePipeline.init` with no default — the same "no caller can forget to connect the speaker" reasoning, now said three times.
- `act(on:for:)` (widened to take the matched `CapturedNotification`, needed to render the template) stays an exhaustive switch, so the compiler forces every new case to be handled: `.speak` renders the template via `SpeechAction.rendered(for:)` and calls the `speak` closure; `.soundAndSpeak` renders the template and calls the `soundAndSpeak` closure, which is the sole `AlertPlayer.outcome(ofPlayingAndSpeaking:…)`-backed path (Task 3) — never two separate calls composed in `CapturePipeline` (ruling 8).

## Found while building, and settled

- _Not every voice renders at 22,050 Hz._ The Eloquence voices (Eddy, Flo and others) render at 16,000 Hz. Measured before Task 2; the speech node is wired at 22,050 Hz, and anything else is converted with one `AVAudioConverter` per utterance, so the resampler keeps its state across buffers (ruling 5).
- _Calibration has its own synthesizer._ It was first put on the alert synthesizer, to warm it. Review showed, and a probe confirmed, that a synthesizer says one thing at a time: an alert would wait up to ~2.5 s behind a calibration, or be lost behind one that hung. Calibration now runs on a second held synthesizer, which is stopped if it times out after 15 s. The alert synthesizer is warmed by a silent render that any alert cuts off (rulings 6 and 7).
- _Speech that stops arriving still ends._ A watchdog ends an alert's speech part if the synthesizer has not finished within 15 s, exactly once: ended twice, a sound-and-speech alert would be declared over while its sound played on. Found in review.
- _A sound set aside comes back too._ Speech was remembered across a change of alert kind, but a sound was not: a trip through Speech, Silent or No Alert replaced Hero at +6 dB with Glass at 0 dB. `AlertEditing.SetAside` now holds both. Found in review.
- _Nothing of a part is heard after it has ended._ Buffers arriving after the watchdog ended a line were still scheduled while its alert's sound played on; they are now dropped. Found in review.
- _A voice whose audio cannot be played is refused when it is measured._ Calibration sends its buffers through the same converter alerts use; a line that still produces nothing playable is logged, without its words. Found in review.
- _Outcomes are typed, not composed sentences._ Instead of ruling 14's single `.failed` with a sentence built where it happens, each partial failure is its own case — `.couldNotSpeak`, `.playedButNotSpoken`, `.spokeButNotPlayed` — and the wording lives in `InspectorRowText`, tested. `.failed` keeps its meaning for sounds, unchanged.
- _Voices are checked inside `SoundCheck`._ A required `voices:` member, rather than a separate `VoiceCheck` threaded through every call site: every place that checks a rule then checks both, and none can forget voices (ruling 11).
- _Offline, a part finishes when rendered._ `.dataPlayedBack` never fires in offline rendering, so completion tests could not observe it; live, it is still "played back".
- _The latency log is at notice level._ At info level it is kept in memory only, and would be gone by the morning it exists to be read on. Measured live: "speech began 18.3 ms after it was asked for", for a voice warmed when the rules loaded.
- _Read & Speak._ The voice pane is called Read & Speak on macOS 26 (Spoken Content before). The link `x-apple.systempreferences:com.apple.Accessibility-Settings.extension?SpokenContent` opens it, checked by hand.

## Found in review, and settled

Three independent reviews ran over the first draft, each checked against the code rather than taken on trust, and the draft was then read against the code once more.

- _A combined alert cut off its own sound._ Built as `play` then `speak`, each claiming "an alert is starting, stop everything", the second call stopped the sound the first had just scheduled. Every alert now claims the interruption state once, through `beginAlert()` (rulings 8 and 9).
- _Calibration blocked the main thread._ It was first placed inside `RuleStore.reload()`, and then inside `speak()` with a nested run-loop pump. The first could freeze launch, Reload Rules and Save for up to 2.5 s. The second, inside the Accessibility callback, could re-enter the capture pipeline mid-alert. Warming and calibration are now asynchronous, and an alert never waits for them (rulings 4, 6 and 7).
- _A sound-and-speech rule skipped the sound-name check._ `reasons(for:…)` matched `.sound` only. It now reads the sound name and voice from whichever case carries them (ruling 2).
- _`PurityTests` did not forbid AVFoundation_ although the constraints said it did. Task 1 adds it.
- _Failure wording would have contradicted itself_ ("Could not play: played Glass, but could not speak"). Each failure's sentence is now composed where it happens (ruling 14).
- _A voice has no "unusable" state to check at load._ No installed voice failed to render in any trial, so validation is by membership only (ruling 11).
- _Refuted_: filtering the rule editor's voice picker to the system's language, on the reasoning that the spoken template is "always English." The template's placeholders are filled from whatever notification matched — an app name and a title in whatever language that app and the user's Mac produced them in — so a language filter would hide the right voice for a non-English banner. Ruling 12 keeps the picker unfiltered; its reasoning is broadened to say why explicitly, rather than resting on the Siri point alone.
