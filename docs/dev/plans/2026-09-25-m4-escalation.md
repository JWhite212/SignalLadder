# M4: Alerts That Keep Going Until Acknowledged — Implementation Plan

> **Execution:** each task is implemented with its tests, committed behind a gate (full suite green at the expected count, zero build warnings), and then independently reviewed against the requirements below.

**Goal:** Let a rule's alert keep going after its first sound — a persistent panel, a repeating sound, then a Shortcut — until the user acknowledges it, several independent escalations at once, without ever making two alarms sound together, and without assuming the timers behind any of it are reliable across a real sleep.

**Architecture:** `Rule.alert` (tier 1) is untouched. A rule gains a second, independent, optional field, `escalation: Escalation?`, holding tiers 2–4: a delayed panel, a capped repeat, and a delayed final action that is either an alert or a Shortcut. The rules format moves to version 4 on the same "lowest version that can hold it" and "an older build refuses rather than misreads" discipline versions 2 and 3 already established. Every data type and every rule of when a tier is due, capped or stale is pure code in `NotificationCore`, proven by advancing an injected clock — never a real `Timer`, never a real wait. `EscalationCoordinator` is a `@MainActor final class`, not the spec's `actor`: every other piece of alert state in this codebase already is, its timers already run on `RunLoop.main`, and the spec's stated reason for an actor — timers racing acknowledgement across queues — does not hold when both are on the same queue, which they are here. The coordinator drives `AlertAudio`'s existing, unmodified `AlertPlayer` through the very closures `CapturePipeline` already uses for tier 1, so "a new alert cuts off one still playing" (§5.15) needs no second mechanism — it is the same mechanism, called again. Two new leaf targets carry the two capabilities that touch what `NotificationCore` may not and what the untested app target should not own alone: `AlertPanel` (AppKit: the borderless, stacking, non-activating panel) and `ShortcutRunner` (`Process` and a swept, `0700` temporary directory, its outcome reported asynchronously so a Shortcut that legitimately runs for minutes never blocks a timer callback or the main run loop) — following `AlertAudio`'s and `RuleStorage`'s own precedent of a small target with its own tests rather than untested code in `SignalLadder`. The app target wires a real `Timer`-backed scheduler, the real panel, the real runner, a best-effort global hotkey, a sleep/wake observer, and the `beginActivity` assertion — all as injected closures, exactly as sound and speech already are. Snooze is not part of this milestone (Ruling 3).

**Tech Stack:** Swift 5.9, Foundation (`Timer`, `RunLoop`, `Process`), AppKit (`NSPanel`, `NSWorkspace`), `Carbon.HIToolbox` (the global hotkey), the existing `AVFoundation` graph in `AlertAudio` (unchanged), XCTest.

**Spec:** `docs/dev/specs/2026-09-11-macos-notification-router-design.md` — §5.7–5.8 (the ladder's shape — departed from, Ruling 1 and 5), §5.12 (repeat capping), §5.15 (`EscalationCoordinator` — departed from, Ruling 2), §5.16 (`ShortcutRunner`'s temp-file handling and launch semantics — Ruling 19, and the audio graph it reuses unmodified), §5.17 (`AlertPanel`), §5.18 (`SnoozeController` — out of scope, Ruling 3), §7.1 (status-item precedence), §9 (health channels — unaffected, but its own "never claim health it cannot demonstrate" discipline shapes Ruling 14), §11 (the two assumptions this milestone must verify), §12 (the M4 row), §14 (provisional tier defaults). §2.1's two named privacy exceptions gain no third: Tier 4's temp file is the second one, already named there.

**Measured groundwork:** `docs/dev/notes/2026-09-11-m1-findings.md`, §"M4 groundwork (2026-09-25)"; `docs/dev/spikes/app-nap-timers.swift` and `alert-panel.swift`, read in full.

## Global Constraints

- **Tests never make a sound, show a window, run an external process, or wait on a real clock.** Ladder timing is proven by advancing an injected scheduler synchronously; the panel's construction is proven by reading its properties back without ever ordering it on screen; `ShortcutRunner`'s process call is proven through an injected launcher whose fake process reports its own exit only when the test tells it to — never a real spawn of `/usr/bin/shortcuts`, and its short launch-grace race (Ruling 19) is proven the same way, with an injected interval, never a real one. Where a live surface genuinely cannot be proven this way — the panel over a full-screen app, the hotkey's permission behaviour, a real Shortcut's exit, a Mac that actually idle-sleeps — it is a human check in Task 7, not a gap papered over with a fake.
- **`NotificationCore` stays pure** (`PurityTests`). The ladder's data types, its validation, and every decision about when a tier is due, capped or stale live there. `NSPanel`, `Carbon`, `Process`, and the real clock stay in `AlertPanel`, `ShortcutRunner` and `SignalLadder`, exactly as `AVFoundation` already stays in `AlertAudio`.
- **One alert claims the audio graph at a time** (§5.15), and this milestone adds no second way to *claim* it. Tier 1, a tier-3 repeat and a tier-4 alert all reach `AlertPlayer` through the same three closures `CapturePipeline` already holds; the coordinator is a caller of `AlertPlayer`, on the same terms `CapturePipeline` already is, never a parallel path. The one addition this milestone makes to `AlertPlayer` itself is a public `silence()` (Ruling 8) — an unconditional stop used only once the coordinator can prove nothing is left to interrupt. That is a second way to *give up* the graph, built from a stop-and-disown sequence `AlertPlayer` already runs for an unrelated reason; it is not a second way to claim it.
- **Notification content is never persisted** except through the one bounded exception §5.16 already names and §2.1 already lists: Tier 4's temp file. It holds exactly four fields — `appNameGuess`, `title`, `subtitle`, `body` — and never `rawText` (which can carry more of the AX tree than any Shortcut needs) or the two fields with no meaning outside this app, `timestamp` and `subrole`. The file is `0700`, deleted in a `defer` the instant the shortcut process actually terminates — which can be well after Tier 4's own outcome is already reported (Ruling 19) — and the per-run directory is removed both when the app launches and when it quits, matching §5.16's "removed at app exit and swept on launch" in full, not the launch half alone. An escalation otherwise holds its triggering notification in memory only, for its own lifetime — the same rule the ring buffer already lives by, extended to a second in-memory holder, not a new kind of exception.
- **A version-3 file means exactly what it means today, forever.** `escalation` is additive and optional; nothing about `alert` changes meaning.
- macOS 14.0 floor, non-sandboxed, Developer ID + notarised, no `.xcodeproj` — unchanged.

## Rulings

**1. Tier 1 stays `Rule.alert`, unchanged. The ladder is a second, independent, optional field, `Rule.escalation: Escalation?`, holding only tiers 2–4.** The spec's §5.7 gives `Rule` one non-optional `escalation: EscalationLadder` with tier 1 folded inside it; M3d built one optional `alert` instead and explicitly deferred the ladder to this milestone. Refolding tier 1 into a new `EscalationLadder` now would touch every call site M3d and M3c already built and tested — `CapturePipeline.act(on:for:)`, `AlertMenuText`, `MuteWalkthrough`, the rule editor's alert controls — to move a field that already works. Leaving it where it is and adding the three later tiers beside it is the smaller, more useful change, the same reasoning M3d gave for combining sound and speech into one alert rather than two escalation tiers.

**2. `EscalationCoordinator` is a `@MainActor final class`, not the spec's `actor`.** §5.15 specifies an actor "because timers fire from multiple queues and acknowledgement races them." Nothing else in this codebase is actor-isolated: `CapturePipeline` and `AlertPlayer` are `@MainActor` classes, and `AppDelegate`'s three existing timers (`canaryTimer`, `followUpTimer`, `retryTimer`) all run on `RunLoop.main`. The race the spec worries about is real only if a timer can fire on a queue other than the one `acknowledge` runs on; here every timer fires through an injected `EscalationScheduler` (Ruling 4) whose production implementation is `RunLoop.main`, and every call to `begin`/`acknowledge`/`acknowledgeAll` is itself `@MainActor` — so there is one queue, not several, and the compiler already enforces it, as it does for `AlertPlayer`. An `actor` here would be this app's first, would need its own bridging story with two `@MainActor` neighbours it must call into on every tier fire, and would buy nothing the existing pattern does not already give for free.

**3. Snooze (§5.18) is not part of this milestone, and the spec's own milestone table never actually assigns it one.** M4's row does not mention it; M5's row (conditions, regex) does not; M6 says only "snooze polish," which presumes it already exists. `NotificationCapture` and `NotificationCore` have no reference to it today. It is also, by the spec's own architecture, upstream of and independent from what this milestone builds: §5.18 short-circuits matching *before* `RuleEngine` runs, whereas escalation only begins *after* a match has already happened and its tier 1 has already fired — nothing about how a live escalation's ladder unfolds depends on whether snooze exists. Building it opportunistically here, because the panel it would reuse is being built anyway, would be scope creep into a feature with no assigned milestone and a real design question of its own (global vs per-app, a confirmation panel, persisted state) that this plan does not attempt to settle. One real gap this leaves, worth naming rather than hiding: "acknowledge" means an escalation is handled, not "not now" — this milestone has no gesture for muting an escalation the user intends to deal with later without marking it resolved. That is snooze's job, wherever it eventually lands; inventing a smaller, parallel gesture here would pre-empt a decision this plan has just said belongs elsewhere, so it is named in "Not in this plan" instead of built.

**4. Ladder timing is driven by an injected `EscalationScheduler`, not a real `Timer`, so tests never wait on a clock.** §10's own testing table asks for "injected clock; tier timing, capping, concurrency, sleep-conversion... verified deterministically" for exactly this reason, and nothing in the current suite has an analogue for a multi-second delay. `EscalationScheduler` is a small protocol — `now() -> Date`, `awakeTime() -> TimeInterval` (Ruling 14), `schedule(after:_:) -> Token`, `cancel(_:)` — living in `NotificationCore`. Its production implementation, `RunLoopEscalationScheduler`, wraps a real `Timer` added to `RunLoop.main` (the app-nap spike's own pattern) and lives in `SignalLadder`, since a *real* timer is exactly the thing a test must never wait on, so the real implementation is kept out of the tested target on principle. `NotificationCoreTests` gets a `ManualScheduler`: it holds a virtual "now," and `advance(by:)` moves it forward and fires every due callback synchronously, in order — the whole of Task 3's suite runs in well under a second of wall-clock time however many simulated minutes it covers. `ShortcutRunner`'s own launch-grace race (Ruling 19) is proven the same way, with its own injected interval rather than a real one.

**5. A tier's audible action stays `AlertAction`, unchanged, for tier 1 and tier 3's repeat. Tier 4 is a new, narrower `FinalAction` — `.alert(AlertAction)` or `.shortcut(name:)` — and `.shortcut` is never added to `AlertAction` itself.** The spec's §5.8 puts `.shortcut` inside the same `AlertAction` enum tier 1 uses, which would make it legal, by construction, everywhere `AlertAction` appears — including `Rule.alert`, `AlertPlayer`'s closures, and the rule editor's existing sound/speech controls — none of which know how to run a process or touch a temp file, and none of which should have to. `AlertPlayer` is documented as kept out of `NotificationCore` specifically so the *audio* path can be tested by rendering the real graph offline; a `.shortcut` case reaching it would either be an unreachable case in an exhaustive switch or would force `AlertPlayer` to grow a non-audio side effect it has no business owning. Confining `.shortcut` to `FinalAlert.action` answers, by construction, the open question the spec never settles (should a shortcut be legal on tier 1?): no, because tier 1's type has no such case, and this is the smaller type change of the two available.

**6. Escalation requires a non-nil tier 1, enforced as a save-time problem, not a type-level constraint.** `Rule.alert == nil` already means something specific and deliberate — "match, stay quiet, no decision made" — distinct from `.silent`. A rule with `escalation != nil` and `alert == nil` reads as climbing a ladder that never had a first rung: nothing announces the match at all until tier 2's panel appears, seconds later, which defeats the point of a first, immediate rung. `RuleSetCodec.problems(in:)` gains "has an escalation ladder but no alert — give it at least a silent alert, or remove the escalation," worded like every other problem this function already reports, rather than a `Rule` initialiser that would have to invent a default alert nobody asked for.

**7. Concurrent escalations share the one `AlertPlayer` already built; the coordinator adds no second interruption mechanism.** `AlertPlayer.beginAlert()`'s `generation` counter already makes "a new alert cuts off whatever was playing" true for any two calls to `play`/`speak`/`playAndSpeak`, whoever makes them. Tier 3's repeat and tier 4's alert-shaped final action are refactored to go through the *same* dispatch tier 1 already uses — `CapturePipeline.act(on:for:)`'s switch over `AlertAction?` is lifted into a standalone `AlertActionRunner.run(_:for:playSound:speak:playAndSpeak:) -> AlertOutcome` in `NotificationCore`, called by both `CapturePipeline` (unchanged behaviour, same tests) and `EscalationCoordinator` (Task 3). Two escalations' sounds are therefore serialised for the same reason two ordinary rule matches already are, with no new state anywhere tracking "which escalation currently owns the graph" — because nothing needs to. One consequence of this worth stating rather than discovering later: because tiers 2, 3 and 4 each run on independent per-escalation timers (Ruling 9), several concurrent escalations can each want the graph within the same few hundred milliseconds, and each new claim cuts the previous one off, exactly as it already does for any two unrelated matches today. §5.15's bar — audio is serialised, never mixed — is still met; what it does not promise is that a burst of concurrent escalations *sounds* like anything other than a rapid succession of cut-off fragments. Smoothing that out (staggering repeats, or collapsing several escalations' sound into one shared tone) is not something the spec asks for and is not built here; Task 7 adds a human check for the case where it would be most audible, so the behaviour is heard and judged rather than assumed away.

**8. Acknowledging a single escalation cancels its future timers at once; sound already in flight is only stopped once nothing is left to own it.** `AlertPlayer` has no public "stop without starting something new" *for one escalation among several*, and inventing one for that case still meets the objection Ruling 7 already raises: since `AlertPlayer` tracks only "is something playing," not "whose," a targeted stop from `acknowledge(id:)` while another escalation is still live could just as easily cut off that other escalation's own tier 1, started a moment before. That ambiguity does not exist once nothing else is live. `acknowledge(id:)` — when it turns out to be the last live escalation — and `acknowledgeAll()` — always, since it clears every live escalation — each then call a new closure, `silenceIfIdle`, wired to a new public `AlertPlayer.silence()`. `silence()` is not new logic: it is the stop half of `outputChanged()` (`AlertPlayer.swift:228` — an output device changing must also stop everything without starting anything new): bump `generation`, clear `isPlayingAlert` and `partsPlaying`, stop both player nodes and the engine, and release the speaker. The two share one private helper; `outputChanged()` keeps its own reconnection of the main mixer to the new device, which `silence()` has no reason to do. This is not a second interruption mechanism; it is the existing one, called only when the coordinator can prove, by construction (nothing else remains live), rather than by tracking who owns what, that there is nothing left to interrupt. Every sound is, in any case, already capped at `AlertPlayer.maximumSeconds` (30 s), so the one case this still leaves untouched — acknowledging one of several live escalations, whose sound happens to belong to a different one still running — costs at most a few seconds of a sound that was already about to end.

**9. Tiers 2, 3 and 4 each run on their own timer from the escalation's start, independently and overlapping — never chained tier-after-tier.** §14's own defaults imply this and never say it outright: tier 4 fires at 120s while tier 3, capped at up to 600s, may well still be repeating. A design that gated tier 4 on "tier 3 has finished" would misread the defaults and would have no sensible behaviour for `maxDurationSeconds: nil` (uncapped). `begin(rule:notification:)` schedules all three timers it needs (tier 2's single delay, tier 3's first repeat, tier 4's single delay) against the same `startedAt`, and none is contingent on another's outcome.

**10. On a repeat cap being reached, tier 3 stops scheduling further repeats; the escalation stays live, and the panel stays visible, silently, until acknowledged or converted.** This is §5.12's own resolution, stated here as code: reaching `maxRepeats` or `maxDurationSeconds` (whichever trips first) sets `EscalationSummary.status = .capped`, which is not a terminal state — tier 4 still fires on its own independent timer (Ruling 9), and sleep conversion (Ruling 14) still applies, exactly as it does to a `.live` escalation. Only acknowledgement or conversion ends it.

**11. Shortcut names are not validated when rules load — there is no membership check to run.** Sound names and voice identifiers are checked against `AVSpeechSynthesisVoice.speechVoices()` and the sound library's own contents (Ruling 11 of the M3d plan); the groundwork found no analogue for Shortcuts. `/usr/bin/shortcuts` was only measured to *fail fast* on a missing name (~150 ms, exit 1, "Couldn't find shortcut") — it was never confirmed to support enumeration, and a picker that assumed one exists would either be wrong or silently degrade to nothing. A tier-4 shortcut name is therefore free text, checked only by actually being run, and reported — by name, per §5.16 — the moment that happens to fail, exactly like a sound whose file went missing after the rules loaded rather than before.

**12. Format version 4, gated exactly as versions 2 and 3 were.** `RuleSetCodec.currentVersion` becomes 4. `version(for:)` returns 4 only when some rule has `escalation != nil`, otherwise falls through unchanged to today's 3/2/1 logic — a rule set that never escalates still round-trips at whatever version it always did. A rule with `escalation != nil` read from a file declared below version 4 is a problem naming the rule: "escalation needs `\"version\": 4` — an older SignalLadder reading this file would reject the rule without saying why," worded like the existing version-2 and version-3 messages.

**13. `InspectorEntry` gains a second, separately-mutable field, `escalation: EscalationSummary?`, distinct from `alertOutcome`.** `alertOutcome` and its writer, `CaptureRingBuffer.setAlertOutcome`, are deliberately "written once" — `InspectorEntry.swift` already distinguishes an annotation (never rewritten) from a preview (recomputed freely), and an escalation is neither: it is a fact that genuinely changes over minutes as tiers fire, get capped, get acknowledged, or get converted on wake. Reusing `alertOutcome` for this would either violate "written once" silently or force every future reader of that field to wonder which convention applies. `CaptureRingBuffer` gains `setEscalation(id:_:)`, documented explicitly as the one field on `InspectorEntry` that *is* written more than once, by design, so nobody mistakes it for `alertOutcome`'s convention while reading the file six months from now.

**14. An escalation is converted to "missed while asleep" only when the Mac is known to have slept, and then only when it slept for longer than the staleness threshold — never merely because the escalation has grown old.** A first version of this ruling converted any `.live` or `.capped` escalation older than the threshold on a periodic sweep, wake or no wake. With §14's own defaults — a 300 s threshold, tier 3 repeating for up to 600 s, `maxDurationSeconds: nil` allowed — that would have ended every escalation at five minutes on a Mac that never slept at all, cutting tier 3 off halfway through its own default cap and making "uncapped" mean "five minutes". It also listened for `screensDidWakeNotification`, which is the *display* waking: on this very Mac the display sleeps while the system never can (`pmset`: `SleepDisabled 1`), and the App Nap run measured every timer firing on time through 27½ minutes locked and dark. Converting on a display wake would cancel an escalation that had been repeating correctly the whole time, at the exact moment the user came back to deal with it.

So sleep is measured, not inferred from elapsed time. `EscalationScheduler` exposes two clocks: `now()`, the wall clock, and `awakeTime()`, which in production is `ProcessInfo.systemUptime` — documented as the time the system has been awake, so it stops while the Mac sleeps and the wall clock does not. At every entry point — each of an escalation's own timer fires, before it acts, and `NSWorkspace.didWakeNotification` (system wake, not the display's) — the coordinator calls `checkForSleep()`: the wall-clock time since its last check, minus the awake time since its last check, is how long the Mac slept in between. If that exceeds `stalenessThreshold` (§14: 300 s), every `.live` or `.capped` escalation that existed before the sleep is cancelled and becomes `.missedWhileAsleep(convertedAt:)`; otherwise the check just moves its reference point on and the ladder resumes. This departs from §5.15's wording — "any escalation older than the staleness threshold" — in favour of §14's own row ("above this, convert … rather than resume"), read as the length of the sleep: with the age reading, closing the lid for twenty seconds at 4 min 50 s would end a live escalation; with the sleep reading, it resumes, and a night asleep converts. A main-thread stall is not a sleep — both clocks advance together — so it converts nothing: late timers simply fire late, and nothing is ever labelled "asleep" that was not. That removes the need an earlier draft had for a second, "no response for over five minutes" wording, and for the periodic sweep that produced it: an escalation with nothing left to fire has nothing stale to fire, and the wake notification still converts it for display.

This is robust to what the groundwork could not measure. Whether a real `Timer`'s remaining time counts the sleep or not, whichever of a tier's timer or the wake notification arrives first runs the same check first, and a tier never acts on stale state. This Mac cannot sleep (`SleepDisabled 1`) and has not since it booted (`kern.sleeptime` 0; wall clock and awake time agree to within 2 s over 8 days), so the two clocks diverging across a real sleep is documented behaviour, not measured behaviour — Task 7 checks it on a Mac that sleeps. Tests prove the whole rule with `ManualScheduler`, whose `advance(by:)` moves both clocks and fires what falls due, and whose `sleep(for:)` moves only the wall clock and fires nothing — so a test sleeps the "Mac" without sleeping the test machine.

**15. The `ProcessInfo.beginActivity(.userInitiated)` assertion is claimed and released by the app target, signalled by two injected closures, and held only while some escalation still has a tier left to fire.** `beginActivity` is a system-level assertion, not a pure computation, so it stays out of `NotificationCore` on the same principle that keeps `NSPanel` and `Carbon` out. The coordinator calls `beginPowerAssertion()` when an escalation begins with a tier scheduled while no other has one pending, and `endPowerAssertion()` the moment no escalation has anything pending — acknowledged, converted, or simply finished: tier 2 shown, tier 3 capped or absent, tier 4 fired or absent. A capped escalation whose tier 4 has already fired stays `.capped` — on the panel and in the menu until acknowledged (Ruling 10) — but no longer holds the assertion, because there is nothing left for the assertion to protect. §5.15 asks for it to be held "only while an escalation is live, so idle battery cost stays nil"; an earlier draft held it for as long as anything was `.live` or `.capped`, which let one ignored, silent, capped escalation hold off idle sleep indefinitely on a laptop on battery — the draft named that cost and relied on the periodic sweep to end it, and Ruling 14 no longer has one. `hasLiveEscalations` still means `.live` or `.capped`, for the menu, glyph and panel; `hasPendingTiers` is the separate question the assertion asks.

The measured reason to hold the assertion is not App Nap — 720 fires across in-use, hours idle, and 27½ minutes locked-and-dark all landed within 3.5 ms of due, assertion or not — it is that `.userInitiated` also holds `PreventUserIdleSystemSleep`, unexercised on a Mac with system sleep disabled, and the one plausible way an escalation could fail to fire on a real Mac at all. Task 7 checks both halves on a Mac that sleeps: held while a tier is pending, released once none is.

**16. The global hotkey is best-effort and never a dependency of acknowledgement.** `RegisterEventHotKey` for ⌃⌥⌘A registered with status 0 on the dev Mac, unattended, and showing the panel left the frontmost app unchanged — both measured. Whether *pressing* it prompts for Input Monitoring on some Mac or macOS version is the one §11 assumption the groundwork could not exercise, because only a person sees a TCC dialog. The plan does not wait on that answer: the hotkey is registered once at launch, calls `acknowledgeAll()` exactly as the menu item does, and a failed registration (or, one day, a declined permission) is logged and otherwise ignored — the menu item and the panel's own button reach `acknowledge`/`acknowledgeAll` by a path that needs no permission at all, per the spec's own stated fallback ("drop the hotkey; panel and menu acknowledgement remain").

**17. `AlertPanel` never shows the notification's title, subtitle or body — only the rule's name and the ladder's own state.** M3d's ruling 13 kept a spoken sentence out of the menu because the menu is seen at a glance, in meetings, on shared screens; a persistent on-screen panel, visible over any app and any Space by design, is a materially larger version of exactly that surface, not a smaller one. `EscalationPanelText` (mirroring `AlertMenuText`/`InspectorRowText`) renders lines like "On-call mentions — tier 2, repeat 3 of 20" and "Acknowledge," never notification content; only the Inspector shows what actually arrived, as it already does for a spoken line.

**18. `ShortcutRunner` and `AlertPanel` are their own SPM targets, on `RuleStorage`'s and `AlertAudio`'s own precedent.** `RuleStorage` exists because file writes are "the one place a bug destroys the user's rules," tested against real folders, outside the untested app target. `ShortcutRunner`'s temp-file handling is the equivalent case for §5.16's privacy exception: it needs its own tests against real temporary directories, and `Process` invocation sits behind an injectable seam so those tests never actually run `/usr/bin/shortcuts`. `AlertPanel` exists because `AlertAudio` already established that AppKit/AVFoundation-facing code is kept out of `SignalLadder` specifically so it can be tested; here, that means constructing the real `NSPanel` and reading its properties back — proving the measured `isFloatingPanel`-resets-`level` trap cannot regress silently — without ever ordering the window on screen.

**19. `ShortcutRunner` reports its outcome asynchronously, races a short launch-grace interval rather than waiting for the shortcut to finish, and deletes the temp file only when the process actually exits.** Three decisions, all forced by §5.16's own words — "delivered at successful launch, not completion... a shortcut that pushes to a phone may legitimately run for a long time" — and by nothing else in this codebase ever blocking the main run loop for an unbounded external call. A first pass at this plan made `run(name:fields:) -> Outcome` a synchronous call, returning once "the process returns." That is wrong on both halves of §5.16 at once: `EscalationCoordinator` is `@MainActor`, its timers fire through `RunLoop.main`, and `AXBannerWatcher` depends on that same run loop for every future capture (`CFRunLoopGetMain()`, `AXBannerWatcher.swift:139`) — a shortcut that "may legitimately run for a long time" would freeze capture, the canary, and every other escalation's timers for exactly as long as it ran; and waiting for the process to fully exit before reporting anything directly contradicts "delivered at successful launch, not completion."

`ShortcutRunner.run(name:fields:completion: @escaping (Outcome) -> Void)` now returns immediately: it writes the temp file, launches the process through an injected, asynchronous `ProcessLauncher` — `(executable:arguments:onExit: @escaping (Int32, String) -> Void) -> Void`, a real `Process` with a `terminationHandler` in production — and races a short, injected `launchGraceInterval` against `onExit`. Whichever fires first decides the single call to `completion`: an exit inside the grace window is `.launched` (zero) or `.failed` (non-zero — this is the measured ~150 ms "Couldn't find shortcut" path); the grace window elapsing with the process still running is also `.launched` — the shortcut is presumably genuinely under way, and per §5.16 nothing here needs to know when, or whether, it finishes. `completion` fires exactly once; if `onExit` fires later still (say, a shortcut that runs for a while and then fails), the temp file is deleted but nothing is reported a second time — matching §5.16's own "it does not retry," which this plan reads as "does not retry, or re-report" once delivery is already recorded. The grace interval is 1 s, from a real run (findings, 2026-09-29): a missing Shortcut fails in 0.07–0.15 s, and `shortcuts run` spends about 0.2 s of its own before a real Shortcut's actions begin, so a second is several times the slowest failure yet far too short to stall a ladder. A Shortcut that fails later than that, inside its own actions, counts as launched — which is what §5.16 asks.

The temp file and its directory are deleted in `onExit`'s real handler, whenever that actually fires — immediately, if the process was already fast; considerably later, if the grace window elapsed first and the shortcut kept running — which keeps §5.16's "deleted in a `defer` immediately after Process termination" literally true regardless of which race won. `EscalationCoordinator.runShortcut` takes the matching shape — `(String, CapturedNotification, @escaping (FinalOutcome) -> Void) -> Void` — so tier 4's dispatch never blocks the coordinator either. Tests supply a fake `ProcessLauncher` whose `onExit` the test calls itself, whenever it chooses, and a fake grace interval advanced the same way `ManualScheduler` advances everything else (Ruling 4) — proving the race deterministically, never spawning a process and never waiting on a real clock.

Three things the draft left unsaid, each of which would have been a bug. First, `Process.terminationHandler` runs on a background queue, and `EscalationCoordinator` is `@MainActor`; in Swift 5 language mode nothing stops a completion from arriving off the main thread and touching coordinator state, so the production launcher hops to the main queue before calling `onExit`, and the grace race is decided there — one thread, as Ruling 2 requires, and as `AlertPlayer` already does for its own audio-thread callbacks. Second, a pipe nobody reads fills at 64 KB and blocks the process writing to it, so a chatty Shortcut would hang at its first large write: standard output goes to `/dev/null`, and standard error is read as it arrives, keeping only its first 4 KB. Third, a Shortcut can echo its input, so what it prints may be notification content: standard error is used only to tell "not found" from any other failure, and is never logged, stored or shown. `.failed` carries a reason built by the app — the Shortcut is not installed, or it exited with a given code — never the Shortcut's own output. A launch that throws (the executable missing, say) is `.failed` at once, and the temp file is deleted then.

## Task 2: `ShortcutRunner` — the temp file, launched without waiting, deleted when it actually ends

**Files:** `Package.swift`, `Sources/ShortcutRunner/ShortcutRunner.swift` (new target), `Tests/ShortcutRunnerTests/…`

- A new library target, no dependencies — the file-and-process equivalent of `RuleStorage`'s "the one place a bug touches disk," on its own precedent (Ruling 18).
- `ShortcutRunner.Outcome`: `.launched` or `.failed(String)` — Tier 4 "counts as delivered at successful launch, not completion" (§5.16), reported without ever waiting for the shortcut to finish (Ruling 19).

- `ProcessLauncher = (_ executable: URL, _ arguments: [String], _ onExit: @escaping (_ exitCode: Int32, _ standardError: String) -> Void) throws -> Void`, defaulting to a real, asynchronous `Process` launch in production — standard output to `/dev/null`, standard error drained as it arrives and capped at 4 KB, `terminationHandler` hopping to the main queue before calling `onExit` (Ruling 19). - `ShortcutRunner.sweep()`: removes any per-run directory left over from a previous crash or quit, called once at launch, before any escalation can create a new one — and again from `applicationWillTerminate` (Task 5), matching §5.16's "removed at app exit *and* swept on launch" in full. A directory whose shortcut is still genuinely running at quit is removed anyway; this is the same small, spec-accepted risk §5.16 itself takes rather than blocking quit on an external process finishing.
- Tests, against real temporary folders (as `RuleStorageTests` already does): the per-run directory is `0700`; the JSON file holds exactly the four given fields, and only those; the file and directory are gone once the fake `onExit` fires, on both a fake success and a fake failure, whether that happens inside or after the grace window; a directory left over from a simulated crash is removed by `sweep()`; two calls to `run` never collide on the same per-run directory name; `completion` fires exactly once, from whichever of the fake `onExit` or the fake grace interval resolves first; a launcher that throws is `.failed` at once and leaves no file behind; a fake standard error holding a fixture notification's title never appears in any `.failed` reason, while one saying "Couldn't find shortcut" is reported as the Shortcut not being installed; a later `onExit` call, simulating a shortcut that goes on to fail well after launch was already reported, still deletes the temp file but never calls `completion` a second time.

## Not in this plan

Snooze and `SnoozeController` (§5.18) — deliberately (Ruling 3), not merely deferred. A "quiet this one for now" gesture distinct from acknowledge — the real gap Ruling 3's own deferral leaves open; it belongs with snooze's own eventual design, not as a smaller mechanism invented piecemeal here. Text DSL, regex, and the `onCall`/`screenLocked`/`frequencyAtLeast`/time-window conditions (M5) — escalation's tiers are pure timing and action semantics over an existing match, and need none of them. Do Not Disturb / Focus suppressing the banner capture an escalation would otherwise start — an existing, pre-existing gap in the capture layer (M1/M2), invisible to the escalation coordinator by construction, since it never sees a match that was never captured; flagged as a human check (Task 7), not solved here. Automatic fallback to a local sound when a Tier 4 Shortcut fails — §5.16 says plainly that a failed Shortcut "does not retry"; Tier 3's own independent repeat (Ruling 9), while it is still running, is already the audible channel for exactly this case, and after it caps, §5.12's own silence-but-visible resolution (Ruling 10) is a deliberate design choice, not a gap to paper over with new escalation-of-escalation logic. A Settings window for user-adjustable tier defaults (§7.5) — §14's defaults stay hard-coded constants, as sound and speech's own defaults already are; making them user-adjustable needs the Settings window M3d already deferred, not a new one invented here. Enumerating installed Shortcuts for a picker — no membership-check API was confirmed to exist (Ruling 11); the field stays free text. Output-device-per-escalation routing (§5.16's "one engine per targeted device") — every escalation already shares the one `AlertPlayer`/one output device this app has always assumed; multi-device routing is a pre-existing gap, not one this milestone opens. Staggering or otherwise coordinating concurrent escalations' audio beyond simple serialisation (Ruling 7) — the spec's own bar ("serialised, not mixed") is met; anything more elaborate is a UX refinement this plan surfaces as a human check, not a mechanism it builds. Verifying macOS's actual behaviour under memory pressure, or a synthesiser/timer's exact fate beyond what the M3d and M4 groundwork already measured — logged and live-checked, not proven, exactly as M3d left it.

## Found in review, and settled

Three independent reviews ran over the first draft, each checked against the code and the spec rather than taken on trust.

- _`AlertEditorView` was not already generic over `Binding<AlertAction?>`._ The draft claimed Task 6 could mount it a second and third time "as-is," citing a note from M3c that does not exist; every control inside it in fact closes over `rule.alert` directly. Task 6 now refactors the view first, to `action: Binding<AlertAction?>`, before reusing it for tiers 3 and 4.
- _`AlertPanel` referenced types `EscalationCoordinator` had not yet defined._ The draft's Task 3 used `EscalationSummary` and an undefined `EscalationPanelRow` before either existed, which cannot reach a green build on its own given this plan's own execution discipline. The panel is now built after the coordinator (Task 4, following Task 3), and reuses the `(EscalationID, EscalationSummary)` tuple the coordinator already exposes rather than a second, never-specified row type.
- _A repeat cap and sleep conversion contradicted each other._ Ruling 10 said a capped escalation stays eligible for sleep conversion; the coordinator's own test list said the opposite. The test is now written to match the ruling, which is the one grounded in §5.12 and §5.15's own reasoning.
- _Tier 2's worked JSON example used the wrong key._ `PersistentAlert.delaySeconds` was written as `"afterSeconds"` in the example, which `rejectUnknownKeys` would refuse. Fixed in Task 1's worked example and added as its own test.
- _`acknowledgeAll()` did not actually stop sound already playing_, despite the spec's "one gesture stops everything" framing — a real gap, since `AlertPlayer` had no public way to stop without starting something new. `AlertPlayer` gains `silence()` (Ruling 8), built from the exact stop-and-disown sequence `outputChanged()` already runs for an unrelated reason, called only once the coordinator can prove nothing is left to interrupt.
- _Ruling 15 named a release condition, "fully finished," with no corresponding status_, and one that contradicted Ruling 10's "capped is not terminal." The first fix held the assertion for as long as anything was `.live` or `.capped`; the check against the code below replaced that with "while a tier is still pending", which needs no status of its own.
- _The sleep-conversion backstop could go permanently silent for the ordinary case_ — once an escalation's own tiers had all fired, nothing was left to check it again short of the wake notification. The first fix, a periodic sweep converting anything older than the threshold, turned out to be the plan's worst defect, and was replaced; see below.
- _"Missed while asleep" would have been reported for a stall that was never actually a sleep_ — true of an elapsed-time signal. The first fix added a second wording for it; measuring sleep directly (Ruling 14, below) made both the ambiguity and the second wording unnecessary.
- _§5.16's "removed at app exit" half of the temp-directory guarantee was dropped_, leaving only "swept on launch" in the draft's Global Constraints and Task 2. `applicationWillTerminate` now sweeps a second time (Task 5), matching the spec in full.
- _Which fields go into a Tier 4 Shortcut's temp file was never actually said_ — a real gap, given this is the one place notification content is deliberately allowed to touch disk. Now stated exactly: `appNameGuess`, `title`, `subtitle`, `body`; never `rawText`, `timestamp` or `subrole`.
- _`ShortcutRunner.run` was synchronous, called from a `@MainActor` timer callback on the same run loop `AXBannerWatcher` depends on for capture_ — a real defect, not a style note: a genuinely long-running Shortcut would have frozen the whole app, and waiting for the process to return before reporting anything contradicted §5.16's own "delivered at successful launch, not completion." `ShortcutRunner` is now asynchronous throughout, with a short, injected launch-grace race in place of a blocking wait (Ruling 19).
- _Refuted_: that a failed Tier 4 Shortcut should automatically fall back to playing a local sound. §5.16 states plainly that a failed Shortcut "does not retry"; Tier 3's own independent repeat is already the audible channel for this case while it is still running, and §5.12's cap-then-silence behaviour is a deliberate resolution (Ruling 10), not an oversight to compensate for.
- _Refuted_: that concurrent escalations' rapid, cut-off audio fragments during an incident storm should be smoothed by staggering repeats or collapsing several escalations into one shared tone. §5.15's own requirement — serialised, never mixed — is met as built; nothing in the spec asks for cross-escalation audio coordination beyond that, and inventing it now is scope this milestone's row does not list. A human check makes the behaviour visible instead (Task 7).
- _Refuted_: that a single `acknowledge(id:)` should track which escalation most recently claimed the audio graph, so it can force-stop that escalation's own sound specifically. This is buildable, but it is real, additional state for a case Ruling 8's original reasoning already bounds acceptably: every sound is capped at 30 seconds regardless, so the cost of not interrupting a single acknowledged escalation's own tail is small and finite. `acknowledgeAll()` — where the ambiguity Ruling 8 worries about cannot arise, because nothing else is left — gets the fix instead.
- _Refuted_: that this milestone should ship a lightweight, per-escalation "quiet this one" gesture now, distinct from acknowledge, to cover the gap snooze's deferral leaves. The gap is real and is named in Ruling 3 and "Not in this plan," but building a smaller, parallel mechanism ahead of snooze's own design would pre-empt a decision this plan has explicitly left to whichever milestone picks snooze up.

## Found checking the plan against the code

The reviewed plan was then read against the source it names, as the M3d plan was. Each finding below changed the plan; line references were confirmed (`AlertPlayer.swift:228`, `RuleDetailView.swift:67`), and the JSON shapes in Task 1 match `docs/rules-format.md`.

- _The staleness sweep would have ended every escalation at five minutes, asleep or not._ It converted anything `.live` or `.capped` and older than 300 s, on a timer, with no sleep required — so on an awake Mac, tier 3 was cut off halfway through §14's own 600 s default cap, and an uncapped repeat meant five minutes. It also woke on `screensDidWakeNotification`, the display, which on this Mac sleeps and wakes while the system never can. Ruling 14 now measures sleep — wall clock against `ProcessInfo.systemUptime`, which stops while the Mac sleeps — checks it at every tier fire and on `didWakeNotification`, and converts only after a sleep longer than the threshold. The periodic sweep, and the "no response for over five minutes" wording it needed, are gone. A test now advances an hour awake and asserts nothing converts.
- _One ignored, capped escalation would have held off idle sleep indefinitely._ The assertion was tied to `.live` or `.capped`, and relied on the sweep above to end it. It is now held only while some tier is still pending (Ruling 15), which is what it exists to protect and what §5.15's "idle battery cost stays nil" asks.
- _Nothing wrote an escalation onto its Inspector row._ `CaptureRingBuffer` is keyed by row id; `begin(rule:notification:)` never received one, and the coordinator had no way to report a change. `begin` now takes the row's id, and the coordinator reports every change through `recordSummary`.
- _A failed tier 3 or Shortcut was reported nowhere._ §5.16 asks for a warning on the Inspector row and a status-item badge. Both now go through the surfaces tier 1's failures already use, with a failed Shortcut held apart from sound failures, so tier 3's next repeat cannot clear a failure to page the phone (Task 5).
- _A Shortcut's exit would have reached `@MainActor` state from a background queue_ — `Process.terminationHandler` runs off the main thread, and Swift 5 language mode does not stop it. The launcher now hops to the main queue first (Ruling 19).
- _A chatty Shortcut would have hung, and its output could have leaked what it was given._ An unread pipe blocks its writer at 64 KB, and a Shortcut can echo its input, which is notification content. Standard output is discarded, standard error is drained, capped, and used only to recognise "not installed", and a failure's reason is always the app's own words (Ruling 19).
- _Refactoring `AlertEditorView` to an action binding would have carried set-aside state from one rule to the next._ The view resets it on `.onChange(of: rule.id)`, which an action binding cannot see; each mount now takes `.id(rule.id)`. The plan also promised to rewrite the view's "existing tests", which do not exist — `SignalLadder` has no test target — so the proof is `AlertEditing`'s suite, unchanged, and a live check (Task 6).
- _`AlertEditing.Kind.shortcut` would have put a Shortcut in Tier 1's picker_ — the leak Ruling 5 forbids, one layer up. Tier 4's choice lives in a new `EscalationEditing` instead.
- _Smaller corrections:_ `silence()` shares only the stop half of `outputChanged()`, not its reconnection of the mixer (Ruling 8); the separate `runFinalAlert` closure was a second route to the same three audio closures, and is dropped (Task 3); the panel lists only escalations whose tier 2 has shown (Task 3); Test Shortcut runs with the sample notification, never a real one, and is not refused during an alert, since it never touches the audio graph (Task 6); the Shortcut's temp file is `0600` inside its `0700` directory (Task 2).
